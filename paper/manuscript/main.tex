\section{Introduction}

SCRIMMAGE provides a plugin-based environment for multi-agent robotics
experiments \cite{demarco2018}. Since its publication, the field has moved
toward robots that share maps and plans over limited links, planners that
evaluate many alternatives on accelerated hardware, and teams that serve
continuing streams of tasks. This paper asks which of these developments
change the experiments a multi-agent robotics testbed should support, and what
evidence would justify building that support.

We focus on three research questions, each paired with the capability it
would need and an experiment that could show whether that capability matters:
\begin{description}
  \item[RQ1:] When does sharing information improve team performance?
  \item[RQ2:] When does more planning computation improve the outcome?
  \item[RQ3:] When does a larger team stop completing more work?
\end{description}

Answering these requires a testbed whose results can be trusted, so that a
different outcome can be attributed to the algorithm rather than to its setup.
We therefore first establish a baseline: SCRIMMAGE-RS, a Rust implementation
that retains SCRIMMAGE's simulation structure. We check that it behaves like
SCRIMMAGE, that experiments are easier to set up and repeat, and that it runs
at comparable cost (Section~\ref{sec:baseline}).

\section{SCRIMMAGE and What Has Changed}
\label{sec:original}
\label{sec:background}

SCRIMMAGE was built to simulate many interacting aerial robots without
requiring expensive physics for every experiment \cite{demarco2018}.
Researchers could replace motion, sensor, network, and behavior models while
keeping the same simulator. Its original paper already described deterministic
execution, batch runs, cluster deployment, and ROS, MOOS, and OpenAI Gym
connections. In its predator/prey experiment, repeatedly switching to the
nearest prey performed worse than committing to a target: the pursuers could
be distracted just before a capture. That is the kind of behavioral result
a testbed should make easy to investigate.

Table~\ref{tab:timeline} connects selected developments since then to the
experiments they motivate. Many new coordination algorithms fit SCRIMMAGE's
existing roles for sensors, networks, controllers, and metrics without
changing the engine. A core upgrade is justified only when an experiment needs
a shared capability that these interfaces cannot express clearly, or when the
existing execution model imposes a measured cost. We distinguish these cases
from reusable experiment models throughout.

\section{A Validated Baseline}
\label{sec:baseline}
\label{sec:upgrades}

This section describes SCRIMMAGE-RS and summarizes three checks: that it
behaves like SCRIMMAGE, that an experiment is easier to build in it, and what
it costs to run. The details are in the appendices.

\subsection{SCRIMMAGE-RS}

Each entity owns its autonomy, controllers, motion model, and sensors.
Interactions, networks, and metrics operate on the world. An autonomy chooses
a desired command; controllers turn it into motion-model inputs; the motion
model advances the state. Sensors then produce observations, interactions
apply effects such as collisions, networks deliver messages, and metrics
update scores. The engine finishes each phase before starting the next, even
when entities run on different CPU workers.

User plugins live in a workspace crate and register with the same
\texttt{scrimmage} executable as the stock models. A plugin owns its parameters
and state; the engine handles scheduling and message delivery. XML and YAML
missions load into one typed scenario; YAML adds shared entity templates and
parameter sweeps, and the simulator checks the scenario and plugin parameters
before running. A run saves trajectories, events, scores, and a manifest, with
Rerun for recorded visualization. Sweeps write one result row per case and can
be split into local processes or Slurm array shards, although cluster
submission has so far been tested with a mock scheduler.

\subsection{Behavior}
\label{sec:parity}

Does SCRIMMAGE-RS behave like SCRIMMAGE? We ran the same mission files in both
and compared not only where every agent went, but also what each agent
believed, what its sensors reported, what each plugin commanded, and when every
message arrived (Appendix~\ref{app:parity}).
\begin{itemize}
\item \emph{They agree.} All 13 hand-written missions and 100 randomly
generated scenarios match. Positions agree to under a nanometre, usually to
about $10^{-14}$~m, which is floating-point rounding.
\item \emph{The comparison is strict enough to catch real mistakes.} To test
it, we introduced 12 small, realistic errors into a copy of the Rust code, such
as a controller gain 1\% too high or a message arriving one step late. The
comparison flagged every one.
\item \emph{Long runs mostly hold.} Eight of ten runs of up to 1{,}000~s
match throughout. In the other two, an aircraft oscillating in its control
loop drifts apart after 26~s and 69~s, ending less than 0.2~mm apart; one is
consistent with rounding sensitivity, the other is unresolved.
\item \emph{Every other difference is a C++ bug that Rust fixes or a
deliberate choice,} such as C++ scoring late-spawning teams as NaN; all are
listed in Table~\ref{tab:differences}.
\end{itemize}
This holds for the models and configurations we tested
(Appendix~\ref{app:coverage}), not the whole C++ plugin catalog.

Both give the same answer: the chaser catches the target at 26 and 30~m/s, at
45.3~s and 32.0~s, and not at 18 or 22~m/s. The difference is in the work
around the model. The mission files are the same length, but the YAML one
states shared setup once, and its sweep needs no edits to the mission. Checking
matters most: with the end time mistyped as \texttt{ending} and the speed as
\texttt{initial\_sped}, C++ ran without a warning for its default 50~s at the
plugin's default 24.3~m/s, and the chaser never caught the target. SCRIMMAGE's
own test missions \texttt{straight\_cpu\_mul.xml} and \texttt{straight\_gpu\_mul.xml}
carry such a typo (\texttt{motion\_multipler}), so they never run substeps. In
YAML, the same mistakes stop the run before it starts.

The plugin code is similar in size (54 lines of C++ against 82 of Rust, which
also declares its ports and checks its parameter). On the C++ side, the
generated plugin does not compile until its placeholders are fixed, and neither
batch script runs, because both need a Python package that is no longer in the
branch. Appendix~\ref{app:rq2} gives the details, and \texttt{paper/rq2/} holds
both versions and the commands.

\subsection{Cost}
\label{sec:performance}

We ran the same four missions in both simulators on one laptop (an Apple M2
Pro): aircraft flying straight, the same with finer physics steps, aircraft
with noisy sensors, and a stream of new aircraft that can collide. Each ran at
several sizes, up to 1{,}024 aircraft (Appendix~\ref{app:performance}).
\begin{itemize}
\item \emph{Speed on one processor core is similar.} We compare speed only on
the two missions where both simulators produce identical results. With finer
physics steps, Rust is 1.25 to 1.5 times faster. On plain straight flight, C++
is 1.25 times faster when built natively, where a known per-step overhead in
Rust dominates, and Rust is up to 1.3 times faster in the container.
\item \emph{Rust uses much less memory,} 2.4 to 7 times less on every mission
and size.
\item \emph{Extra cores help only when there is enough work.} Rust on eight
cores ran the sensor mission 2.3 times faster than on one, but the simplest
missions ran slower: handing out work to the cores every step costs more than
the work itself.
\item \emph{C++'s multi-core mode is unreliable.} It froze in 10 of 178 runs,
gave different answers to the same run when sensors were involved, and was
usually slower than running C++ on one core. We compare against single-core
C++.
\end{itemize}
We measured both in a Linux container and directly on macOS; apart from
straight-flight speed, the findings hold in both.

\section{RQ1: When Does Sharing Information Improve Team Performance?}
\label{sec:rq1}
\label{sec:rq4}

\paragraph{What changed}
Kimera-Multi builds consistent maps through peer communication, while RACER
coordinates exploration and workload allocation
\cite{tian2022kimera,zhou2023racer}. These motivate a question beyond adding
radio loss: what information should robots share, and when does its value
outweigh its cost? A comparison is meaningful only if each method receives
the information allowed by the experiment.

\paragraph{What the baseline cannot express}
The retained interface exposes truth contacts to autonomy. Rust separates
owned belief from truth, but a plugin can still read those contacts, and
own-state feedback falls back to truth when no estimate exists. Sensor and
network models alone therefore do not enforce partial observability.

\paragraph{Candidate capability}
An optional observation-only decision interface, with explicit missing
estimates and observation age. Sensors and evaluation would retain access to
truth; existing plugins would retain their current interface.

\paragraph{Experiment}
Compare local decisions, periodic sharing, and selective sharing on the same
exploration task under a fixed message budget. Measure coverage, duplicated
work, and stale decisions, using ideal information as a separate reference
condition. The upgrade's contribution would be a checkable information
boundary; the scientific result would identify when sharing helps. A simple
target-observation model can address this question without implementing a
visual-SLAM system.

\section{RQ2: When Does More Planning Computation Improve the Outcome?}
\label{sec:rq2}

\paragraph{What changed}
Isaac Gym, VMAS, and Isaac Lab show the importance of accelerated workloads
\cite{makoviychuk2021isaacgym,bettini2022vmas,mittal2025isaaclab}. For this
testbed, the question is whether evaluating more alternatives improves team
outcomes enough to justify the computation. That requires measuring both
planning quality and when a decision becomes available.

\paragraph{What the baseline cannot express}
The retained scheduler calls each entity's autonomy separately and joins the
phase before advancing. A costly call slows wall-clock execution without
making its decision late in simulation time. A plugin can already perform
its own calculations or defer its own output, but shared batches across
entities and consistent decision-delay rules require additional support.

\paragraph{Candidate capability}
An optional shared batch interface and an explicit model of decision
availability. Requests would carry observation times; results would take effect
at defined phase boundaries. Prescribed or recorded delays would support
repeatable experiments without letting GPU completion order determine simulated
behavior.

\paragraph{Experiment}
The planned Burn workload could evaluate batches of candidate trajectories.
First compare CPU and GPU execution of the same calculation, including
packing, transfers, and synchronization. Then vary the planning budget and
modeled decision delay, measuring completion, collisions, and expired
commands. The baseline's cost measurements (Section~\ref{sec:performance})
cover execution time; this experiment asks whether the additional computation
changes the decision that can be made in time. Batched inference or scoring
would not imply GPU physics or a batched-world simulator.

\section{RQ3: When Does a Larger Team Stop Completing More Work?}
\label{sec:rq3}

\paragraph{What changed}
RHCR addresses repeated goals, and RACER balances exploration workloads
\cite{li2021rhcr,zhou2023racer}. These motivate measuring sustained useful
work as demand and team size grow. Faster simulation of more robots does not
establish that a coordination method uses those robots effectively.

\paragraph{What the baseline cannot express}
Entity generation and removal already exist, but they do not define task
arrival, ownership, completion, or reassignment.

\paragraph{Candidate capability}
A reusable task model with saved arrival schedules and common task events,
which would make these comparisons repeatable. It should first use the
existing interaction, autonomy, network, and metrics roles. Only a
demonstrated limitation would justify moving part of that model into the core.

\paragraph{Experiment}
Compare allocation methods under identical task arrivals, then increase
demand, team size, and interruptions. Completed tasks per unit time, waiting
time, backlog, and recovery after an agent is lost would reveal where
additional robots help or create congestion. This tests a research capability
beyond the baseline's runtime, even if no scheduler change is needed.
Continuing tasks do not by themselves require continual learning.

\section{Discussion and Limitations}
\label{sec:discussion}

\subsection{What Would Justify an Upgrade?}

Each selected experiment should compare the retained baseline with the
proposed extension, state what the baseline can already express, and isolate
the feature's effect. SMACv2 shows why success on fixed scenarios is
insufficient: some original SMAC tasks admit useful time-only policies
\cite{ellis2023smacv2}. Use held-out layouts, task schedules, or team sizes,
and remove the relevant feedback or communication to check that it matters.
These controls can begin with the existing scenario and sweep tools.

The observation boundary (RQ1) and shared computation (RQ2) are candidates for
core changes. Task models (RQ3) and evaluation cases should begin as research
plugins and experiment support. A focused paper could implement one of the core
candidates and answer its associated question, leaving the others as
motivated future work. Listing features or demonstrating that they run would
not establish their research value.

\subsection{Limits of the Baseline}

The comparison found defects on both sides. Tracing and generated scenarios
exposed C++ defects that trajectories alone would have hidden, and Rust defects
that we fixed, down to the order of floating-point operations. The limits of
the parity claim are:
\begin{itemize}
\item \emph{Scope.} Parity covers the tested configurations of the retained
models, not the full C++ catalog.
\item \emph{Message contents.} Only lifecycle, collision, and sensor messages
are compared by content; other messages, such as auction bids, by delivery only.
\item \emph{Stochastic behavior.} Sensor noise is tested by seven marginal
distributions in one NoisyContacts fixture, not for temporal or cross-axis
dependence, and NoisyState noise is not tested by distribution.
\item \emph{Rounding.} Results agree to rounding, not bit for bit: C++ and Rust
call different math libraries and group some operations differently. Two long
runs diverge late; one is consistent with numerical sensitivity, and the other's
cause is unresolved.
\end{itemize}

\section{Parity Details}
\label{app:parity}

\paragraph{Approach}
Both simulators run the same mission files. C++ comes from the current
\texttt{Ubuntu-24.04} branch, built headless in its own Docker image.

Trajectories alone can hide differences in what agents believe, what their
plugins command, and what messages they send. We therefore added an optional
trace to a separate C++ branch. It records each message delivery (tick,
sender, and receiver), the entities named in lifecycle and collision events,
published sensor readings, each agent's belief, and the commands each plugin
passes to the next. Other message contents, such as auction bids, are not
compared. Rust writes the same trace. Instrumentation that changed C++ would invalidate the
comparison, so every run is repeated on the unmodified build: frames and
summaries must be byte-identical.

Randomized runs only compare if both simulators draw the same random numbers.
The C++ standard leaves its default generator up to each compiler's library, so
the C++ branch can switch spawning to the same fully specified generator Rust
uses. Rust's sensor noise uses its own random streams by design, so noise is
compared by distribution instead of sample by sample.

A comparison that cannot fail proves nothing. Beyond thirteen hand-written
missions, we ran 100 randomly generated scenarios and ten long ones of up to
1{,}000~s, planted twelve plausible porting bugs to confirm the comparison
catches them, and tested the noise distributions. Appendix~\ref{app:method}
gives the details.

\paragraph{Results}
Table~\ref{tab:parity} summarizes the evidence. All curated missions and
generated scenarios pass, and every planted bug is detected. In passing runs,
trajectories agree to $3.7\times10^{-10}$~m at worst and usually to
$10^{-14}$~m or better. No difference was detected in seven NoisyContacts
marginal error distributions at the corrected significance threshold.

Eight of the ten long runs pass. In the other two, an aircraft oscillates in
its control loop, and C++ and Rust exceed the tolerance after 25.7~s and
69.3~s, ending $1.9\times10^{-4}$~m and $7.1\times10^{-5}$~m apart. In the
second, changing one input of Rust by one unit in the last place makes Rust
diverge from itself at about the same time (69.7~s), which is consistent with
numerical sensitivity. In the first, the same control does not reproduce the
divergence, so its cause is unresolved; the trace shows the first difference
in the last digit of a heading computation (Appendix~\ref{app:results}).

In the tested configurations of the retained models,
SCRIMMAGE-RS agrees with SCRIMMAGE in trajectories, the compared sensor and
command values, and message-delivery timing, to floating-point rounding.
Summaries match or are validated against the documented scoring differences.
The exceptions are listed in Table~\ref{tab:differences}.

These results come from the SCRIMMAGE-RS code committed with them (the
retained reports record a hash of every Rust source file) and C++ commits
\texttt{4bdf41fb0} (\texttt{Ubuntu-24.04}) and \texttt{747a28069}
(\texttt{benchmarking-edits}).

\section{Comparison Method}
\label{app:method}

\paragraph{Builds}
A checker builds each C++ branch from a \texttt{git archive} inside the
unmodified upstream dependency image (\texttt{linux/amd64}, GCC~13.3), headless
and single-threaded. \texttt{Ubuntu-24.04} is the unmodified reference;
\texttt{benchmarking-edits} adds only opt-in comparison support. No
model equation is patched. Two command drivers exist in both implementations:
\texttt{MotorSpeeds}, because the upstream multirotor controller no longer
matches the multirotor model, and \texttt{ConstantVelocity}, because no retained
upstream autonomy commands a velocity. Rust runs at 1, 2, and 8 workers, with
recording, and with tracing; all must be byte-identical.

\paragraph{Trace}
Set with \texttt{SCRIMMAGE\_TRACE} in C++ and \texttt{-{}-trace} in Rust. It
records every message delivery (tick, network, topic, sender, receiver, and the
entities in lifecycle and collision events), every published sensor state and
covariance, each entity's belief when its frame is logged, and every output the
next plugin reads. Each mission runs on the unmodified build, the instrumented
build, and the instrumented build with tracing; all three must write
byte-identical frames and summaries.

\paragraph{Criteria}
Frames must contain the same entities at every tick. States, beliefs, and
sensor readings must agree within $10^{-8}$~m, $10^{-8}$~m/s, $10^{-9}$~rad, and
$10^{-9}$~rad/s; outputs within $10^{-8}$; covariances within $10^{-9}$;
summaries within $10^{-6}$. Deliveries must match exactly, in order. The
position limit is 27 times the largest difference measured in a passing run
($3.7\times10^{-10}$~m).
They replace the original 0.01~m and $10^{-3}$, which let a planted
sub-micrometre bug through.

\paragraph{Random draws}
The C++ standard leaves the default random engine and the normal
distribution's algorithm to each standard library. The reference build's
library (GCC's) and the one Rust reproduces (LLVM's) differ in both. With
\texttt{SCRIMMAGE\_LIBCXX\_SPAWN\_RANDOM}, the C++ branch draws spawns from the
standard-defined \texttt{std::minstd\_rand} with the same normal algorithm as
Rust. Without it, the randomized mission differs by up to 8.42~m; with it, it
agrees to $1.4\times10^{-14}$~m. Sensor noise is compared with
fixed-bias, zero-noise fixtures and, separately, by distribution.

\paragraph{Long runs}
Ten generated scenarios run for 1{,}000~s (fixed-wing: 100~s at 0.01~s steps).
A run agrees if every check passes over its whole length. For a run that
diverges, a control changes Rust's initial roll, commanded speeds, and turning
radii by one unit in the last place and measures when Rust diverges from itself.

\paragraph{Summaries and one exclusion}
A differing summary passes only if entity and collision counts match exactly,
and the Rust run's metrics messages reproduce the C++ summary under the C++
scoring rule and the Rust summary under Rust's documented rule
(\texttt{reference/metrics\_model.py}). For entities C++ destroys before
the first step, their first-step trace records are excluded and counted, because
C++ still runs them for that step. No other difference is excluded.

\section{Performance Details}
\label{app:performance}

Tables~\ref{tab:benchmark} and~\ref{tab:benchmark-native} time four workloads
(straight flight, ten controller and motion substeps, noisy state and contact
sensors, and scheduled spawning with collisions) on an Apple M2 Pro, first with
both simulators in one Linux container (\texttt{reference/benchmark.py}) and
then on bare-metal macOS, where unmodified C++ is built with Apple clang
against the library versions Ubuntu 24.04 ships
(\texttt{paper/data/benchmark-native/}). Rust output matches single-threaded
C++ in the first two workloads. Sensing and churn depend on random draws that
the unmodified C++ build makes differently, so their ratios are not speed claims.

Where outputs match, Rust with one thread is 1.0 to 1.5 times faster in the
container. On bare metal it is 1.3 times faster with substeps but 1.25 times
slower on plain straight flight, where its fixed per-step bookkeeping dominates; profiling
attributes about a fifth of that time to building message-endpoint names each
step. Rust uses 2.4 to 7 times less memory.

Parallel speedup depends on each phase carrying enough work. Every phase hands
entities to a thread pool and joins it, which profiling puts at about
35~\textmu s on bare metal and roughly ten times that in Docker's virtual
machine. On bare metal, eight Rust workers beat one with substeps at 1{,}024
aircraft and with sensors at 64 and 128 aircraft (2.3 times at 128), but not
on light workloads or with 32 sensing aircraft; in the container they rarely do. The handoff cost about 7~\textmu s
even with one worker, so Rust now runs single-worker phases on the calling
thread, a third faster on light workloads with identical output.

C++'s own \texttt{multi\_threaded} mode is not reliable. It deadlocked in 10 of
178 runs (each killed after 120~s and retried), its output with sensors differs
between identical runs, and it is slower than single-threaded C++ except with
sensors. Its entity worker waits on a condition variable without a predicate,
so a wake-up can be lost; we did not modify it, and single-threaded C++ is the
baseline.

\section{Rust Self-Consistency}
\label{app:self}

Rust results are byte-identical across 1, 2, and 8 workers, with and without
recording and tracing, and whether a scenario comes from XML, YAML, or Rust
code. Built for another operating system and processor (Linux/amd64 versus
macOS/arm64), events and summaries stay identical in all 248 runs checked and
trajectories differ by at most $5.6\times10^{-11}$~m, because each system's math
library rounds differently (\texttt{reference/platform\_check.py}). This is exact because workers own separate entities, every phase finishes
before the next starts, and random draws are tied to entities and plugins
rather than workers.

\section{The Workflow Example}
\label{app:rq2}

The C++ side used the unmodified \texttt{Ubuntu-24.04} reference image.
\texttt{create-scrimmage-project.py} generated the project, and
\texttt{generate-plugin.sh autonomy FollowNearest} generated the header,
source, parameter XML, and CMake file. The templates on this branch were
reformatted to \texttt{(>{}>{}> PLUGIN\_NAME < < <)}, which the generator's
substitution no longer matches, so four placeholders in the source and three in
the header had to be fixed by hand. The template's example logic already
follows the nearest opponent, so the plugin body is unchanged from it. Running
the plugin requires adding the build and header folders to
\texttt{SCRIMMAGE\_PLUGIN\_PATH} and \texttt{LD\_LIBRARY\_PATH}.
\texttt{run\_experiments.py} and \texttt{scrimmage\_runner.sh} both import
\texttt{scrimmage.utils}, which was removed from the branch, and need
\texttt{pyDOE}, \texttt{pandas}, and \texttt{tqdm}; the \texttt{scrimmage}
command has no option to set a mission variable. The sweep is therefore a
shell loop that writes one mission per speed with \texttt{sed}.
\texttt{paper/rq2/run-cpp.sh} repeats all of this in one command.

The Rust side is the book's first-plugin tutorial: \texttt{follow\_nearest.rs}
in the starter crate, three lines in its \texttt{lib.rs}, a 48-line YAML
mission, and a 9-line sweep file. The same sweep file runs locally with
\texttt{scrimmage sweep} or as Slurm array shards with
\texttt{scripts/bulk\_run.py}. Line counts exclude blank and comment lines;
the C++ count covers the header and source, not the generated CMake file.
Both place the two aircraft at fixed positions, and all four outcomes and
both catch times agree.

\section{Reproduction}
\label{app:reproduction}

From the repository root, with Docker and the sibling C++ checkout on both
branches, \texttt{python3 reference/campaign.py} reruns the C++ comparisons
(agreement matrix, sensitivity, noise, generated and long scenarios, platform),
replaces their folders in \texttt{paper/data/}, and regenerates the tables; with
\texttt{-{}-quick} it runs only the agreement matrix. The individual tools are
in \texttt{reference/}: \texttt{reference\_check.py} (matrix, traces, and
non-interference), \texttt{generate\_scenarios.py}, \texttt{sensitivity.py},
\texttt{noise\_statistics.py}, \texttt{divergence.py},
\texttt{platform\_check.py}, and \texttt{benchmark.py}. The compared missions
are listed in \texttt{reference/missions.txt}, and \texttt{reference/README.md}
documents the builds, tolerances, trace records, and how to add a model. The
C++ branch \texttt{benchmarking-edits} holds the instrumentation as
reviewable commits on top of \texttt{Ubuntu-24.04}.

The campaign does not rerun the rest: the timing in Tables~\ref{tab:benchmark}
and~\ref{tab:benchmark-native} (\texttt{reference/benchmark.py}, and
\texttt{build.sh} and \texttt{run.py} in \texttt{paper/data/benchmark-native/}), the workflow example
(\texttt{paper/rq2/run-cpp.sh} and \texttt{scrimmage sweep}), and the Rust and
Python test suites (\texttt{cargo test -{}-workspace} and
\texttt{python3 -m unittest discover -s reference -p 'test\_*.py'}).
