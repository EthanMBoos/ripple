\title{Ripple: Does Realism Reorder the Leaderboard? A Controlled Fidelity
Ladder for Learned versus Classical Multi-Robot Coordination}
\author{Author names and affiliations to be added}
\maketitle

\begin{abstract}
Learned multi-robot policies are usually trained and compared in simulators
with point agents, exact observations, and messages that are never lost.
Classical methods such as optimal assignment, reciprocal collision avoidance,
and flocking rules assume different things. We ask whether the ranking
between learned and classical policies on standard tasks still holds when
sensing is noisy, messages are lost or late, and the vehicles have real
dynamics. To answer it we built Ripple, a deterministic multi-agent simulator
in Rust. Point agents, multirotors, and fixed-wing aircraft share one world
and one sensing, communication, and estimation pipeline, and each agent acts
on its own belief rather than the true state. Fixed-wing aircraft with
aerodynamic tables, terrain contact, and an external autopilot are built.
Each model is checked against an external implementation or a published
model, and the source of every equation and parameter is recorded. Policies
trained in other simulators run in Ripple unchanged, so learned and classical
policies see the same information, use the same controllers, and run on the
same episodes. On cooperative navigation, circle-crossing collision
avoidance, and flocking with limited communication range, we turn up sensing
noise, communication loss and delay, and vehicle dynamics one at a time. The
classical policies get the same tuning budget as the learned ones, and the
learned policies are trained at the simple setting, the realistic setting,
and with the setting randomized. \textit{[Results pending: where the ranking
changes, which factor changes it, and how much training at the realistic
setting recovers.]}
\end{abstract}

\section{Introduction}

In a multi-agent experiment, the vehicle, sensing, and communication models
decide how each robot's choices play out. Actuator lag delays a response. A
fixed-wing aircraft cannot stop to let another pass. A lost message leaves a
teammate acting on old information. Small differences like these can change
what the team achieves, or they can wash out.

This matters most for learned policies. Multi-agent reinforcement learning is
developed on simulators built for speed, such as the particle environments
\cite{lowe2017maddpg}, VMAS \cite{bettini2022vmas}, and JaxMARL
\cite{rutherford2023jaxmarl}. Their agents move under simple planar physics, and
although noise on observations and messages can be switched on, published
results mostly use exact observations and lossless communication. A policy can
learn to rely on those simplifications. When papers do compare against classical
methods, the two sides often get different information or different tuning
effort (Section~\ref{sec:tasks}). Our question is: \emph{when realism is added,
does the better approach, learned or classical, change, and which part of the
realism changes it?}

Answering this takes a simulator where sensing, communication, and vehicle
dynamics can each be changed while everything else stays fixed, and where
each added model can be trusted. Vehicle models, autopilots, sensors, and
networks each bring their own frames, units, commands, and timing. A model
can match its source on its own and still behave differently once it is
scheduled with the rest of the system. If a ranking changes, we need to know
it was the modeled effect and not an integration bug, so each piece is
checked at its boundary and again in closed loop.

Ripple is that simulator. Its Rust core builds on SCRIMMAGE's plugin design
\cite{demarco2018}, and it agrees with the C++ original to floating-point
rounding on every compared mission (Appendix~\ref{app:baseline}). Aerodynamic
tables, terrain contact, and ArduPilot running in lockstep are integrated; rotor
dynamics are next (Section~\ref{sec:multirotor}). Every vehicle goes through the
same sensing, communication, and estimation stages, which keep the true state
separate from each agent's belief, and every run is byte-repeatable. A learned
and a classical policy can therefore read the same belief, command the same
controllers, and be compared on identical episodes.

We keep two claims apart for every model. Matching an external
implementation shows the equations, conversions, and timing came through
intact. Matching measurements of a real vehicle is a separate and stronger
claim. Reproducing a reference model does not make its estimated
coefficients measured, and adding an autopilot does not validate the vehicle
model it flies.

The paper makes three contributions:
\begin{enumerate}
\item A simulator in which vehicle models, optional physical effects, and
external autopilots share one deterministic execution and information
pipeline.
\item An external check for each integrated model, with the sources of its
equations and parameters and a statement of what the check does and does not
show.
\item A learned versus classical comparison on three standard tasks, with
sensing, communication, and dynamics turned up one at a time, equal tuning
budgets, three training conditions, and a test of whether the ranking holds.
\end{enumerate}

We are looking for reversals: a policy that wins with the simple model and
loses, or fails, once a realistic effect is added, along with the effect
responsible. A ranking that holds is also a result, since it shows where the
simple simulator was good enough.

\section{Related Work}
\label{sec:related}

\paragraph{Simulators for many agents}
PettingZoo standardized how a learner steps a multi-agent environment
\cite{terry2021pettingzoo}. Isaac Gym, VMAS, and JaxMARL moved simulation onto
the GPU, advancing thousands of independent worlds together
\cite{makoviychuk2021isaacgym,bettini2022vmas,rutherford2023jaxmarl}. Since
2025 these tools have moved toward physical fidelity: Isaac Lab adds actuator
models and multi-frequency sensors \cite{mittal2025isaaclab}, Crazyflow
simulates drone swarms in JAX \cite{schuck2026crazyflow}, and
MuJoCo-Drones-Gym models aerodynamic effects on the CPU while its GPU backend
omits them \cite{tayal2026mujocodrones}. Communication is usually
an action channel or part of the observation; queued delivery with delay and
loss comes from co-simulation with a network simulator
\cite{burmeister2025defiance}. Multi-agent testbeds built for many vehicles,
such as SCRIMMAGE \cite{demarco2018}, run simple models and delegate physics to
a separate flight model where needed.

\paragraph{Vehicle dynamics}
JSBSim builds aircraft from coefficient tables \cite{berndt2004jsbsim}.
ArduPilot and PX4 ship their own simulators to test autopilot code
\cite{ardupilotsitl,px4gazebo}, and RotorS models multirotor motors and rotors
in Gazebo \cite{furrer2016rotors}.

\paragraph{Fidelity and evaluation}
Several projects train in a fast simulator and test somewhere more
realistic. Pyquaticus trains maritime game policies with embedded vehicle
dynamics and runs them on uncrewed surface vessels
\cite{crowley2025pyquaticus}. A connected-vehicle benchmark separates the
loss caused by a different control stack from the loss caused by a more
realistic environment \cite{beerwerth2026zeroshot}. BVR Sim moves a policy
between aircraft by having it command per-aircraft controllers
\cite{sun2026bvrsim}. Labiosa and Hanna trained robot soccer policies in a
deliberately low-fidelity simulator, ablated which changes to it let the
policies transfer to real robots, and matched a well-tuned hand-written
behavior \cite{labiosa2025abstract}; their question is what makes transfer
work, not whether added realism reorders learned and classical methods.
Kadian et al.\ measure how well performance in simulation predicts
performance on real robots, with a Pearson correlation and a count of
ranking reversals \cite{kadian2020sim2real}. Li et al.\ ran cooperative
MARL under many kinds of perturbation and found that robustness to one does
not carry over to another, without classical baselines or vehicle dynamics
\cite{li2025robustness}. SMACv2 showed that a fixed benchmark can be solved
without the observations it provides \cite{ellis2023smacv2}, and reviews of
MARL evaluation find inconsistent seeds, metrics, and baselines
\cite{gorsane2022evaluation,papoudakis2021benchmarking}. We found no study
that varies sensing, communication, and dynamics separately on standard
multi-agent tasks and checks whether the ranking of learned and tuned
classical policies changes.

\section{System}
\label{sec:system}

Ripple began as a Rust port of SCRIMMAGE \cite{demarco2018}; its agreement
with the C++ reference is in Appendix~\ref{app:baseline}. This
section describes the properties the fidelity question relies on.

\paragraph{One deterministic tick}
Each tick runs fixed phases: generation; autonomy; controllers then motion in
each substep; sensors; interactions; networks; delivery and estimation
(localization then tracking); metrics; and removal, output, and time advance.
Every phase completes before the next begins,
even when entities run on different CPU workers, and output is byte-identical
at 1, 2, and 8 workers and with recording on or off
(Appendix~\ref{app:self}). Sensor random streams use stable entity and plugin
identities; legacy spawn draws retain their reference order. External
autopilots require their own repeatability checks.

\paragraph{Truth, measurements, and belief}
Sensors read physical truth and produce measurements; estimators turn
measurements and received messages into each agent's belief; decisions and
controllers read only belief. A model of higher fidelity therefore reaches a
decision only through what the agent could have measured or been told.

\paragraph{Scale}
Finding nearby agents and routing messages each cost the square of the team
size in the design we started from. Answering spatial queries from a grid, and
routing each message only to its subscribers, made a 4{,}096-agent step 3.8 and
40 times faster with byte-identical output (Appendix~\ref{app:scaling}).

\paragraph{World resources and autopilots}
Terrain is a shared, read-only world resource that motion models query, for
example for landing-gear contact. ArduPilot's software-in-the-loop (SITL)
autopilot flies a vehicle through a lockstep bridge: each simulation step waits
for the autopilot's outputs and answers with the vehicle's state, and several
autopilots run side by side, one per vehicle.

\section{Evidence at Each Integration Stage}
\label{sec:verification}

The C++ comparison establishes a starting point, not a blanket guarantee for
new models. Each integration needs its own external baseline. We distinguish
three questions:
\begin{enumerate}
\item \emph{Did we preserve the source behavior?} Compare a port against its
source on matched inputs and initial conditions. For a bridge, check the
exchange of states and commands, coordinate conversions, and simulated timing
against the external system's interface and a reference run.
\item \emph{Does the model represent the vehicle in the claimed regime?}
Compare against independent measurements where available. Agreement with
another simulator establishes implementation agreement; it does not establish
physical accuracy. Keep calibration data separate from validation data.
\item \emph{Does the added capability matter for the experiment?} Compare
outcomes, failures, and cost under controlled changes in model effects or
control stack. Report the operating regimes actually visited.
\end{enumerate}

For each comparison, retain the source version, model parameters, frames and
units, input sequence, initial state, timestep, and error measures. State the
comparison tolerance and its rationale before interpreting the result. Start
with forces, moments, derivatives, or command outputs where those are the
integration boundary, then compare trajectories and a closed-loop mission.
Preserve failed comparisons and explain intended departures from the source.
An effect disabled in existing missions must preserve their outputs; a
deliberate defect correction needs a documented new baseline.

These are completion criteria, not claims that the comparisons have run.
Source comparisons belong with each implemented stage, even when physical
validation must wait for data. Each stage also measures execution cost at its
intended team size, so the expense of a few detailed vehicles or external
autopilots is visible.

\section{Fidelity as an Experimental Variable}
\label{sec:fidelity}

To ask whether fidelity changes a result, fidelity must be a controlled
variable: changed alone, with everything else held fixed.

\paragraph{Attributable differences}
Run the same mission, seed, and strategy with a specified model change.
Repeatability makes differences easier to diagnose; attribution also requires
holding other inputs and interfaces fixed. Record controller tuning, decision
periods, sensor and network settings, and initial conditions alongside the
model variant. Core output is byte-identical in the comparisons described in
Section~\ref{sec:system}. Three runs of the runway mission with ArduPlane
(Section~\ref{sec:stall}) also wrote byte-identical output on one machine.
This is evidence for that configuration, not a guarantee for all external
stacks. Across machines and ArduPilot versions it is untested.

\paragraph{Selectable effects}
Each physical effect is an optional parameter of its model, off by default. A
mission that does not set it runs exactly as before, so earlier results and
the agreement with C++ (Appendix~\ref{app:baseline}) stay valid as
features are added. Where an inherited model is wrong rather than incomplete,
it is fixed and the fix recorded.

\paragraph{Model detail, physical evidence, and control stack}
Table~\ref{tab:ladder} separates choices that a single fidelity score would
conflate. Kinematics and rigid-body dynamics change the model structure;
measured parameters change its evidential basis; an external autopilot changes
the control stack. An autopilot can fly an inaccurate plant. A simple model
with measured parameters can be better supported in its operating regime than
a more detailed model with borrowed coefficients. Comparisons should name the
axis changed and the evidence supporting it.

\paragraph{The experiment}
For each task (Section~\ref{sec:tasks}), start at the benchmark's own
setting and turn up one factor at a time: sensing noise, communication loss
and delay, then the vehicle model. Finally turn up all three together. Keep
the policy's command interface fixed; if controllers or tuning change, report
that as its own factor. Measure the ranking, outcome differences, failure
rates, and run cost on paired seeds, with uncertainty across training seeds
and episodes (Section~\ref{sec:learning}). Decide in advance how large a
difference matters for the task before claiming a simpler model is enough,
and record the turn rates, actuator saturation, or message ages actually
reached. A ranking that does not change does not mean the outcomes are equal
or the model is accurate, and a trial that never reaches an effect's regime
cannot show the effect is unnecessary.

Three observations follow. Structure is easy to obtain: every source publishes
its equations. Numbers measured on the vehicle being simulated are rare, and
they come from system identification of one airframe. Borrowed numbers are hard
to see: nothing in RotorS's vehicle files marks its rotor coefficients as
shared, and nothing in the fixed-wing model we inherited records that its
coefficients came from a model its authors called pre-alpha. Each model
in Ripple should therefore state the source of its structure and of its
numbers, and the regime in which they were measured, and claim no more fidelity
than those sources support.

\section{A First Extension: Stall}
\label{sec:stall}

FixedWing6DOF, the fixed-wing model we started from, computes lift as $C_{L0} +
C_{L\alpha}\alpha$ plus
rate and elevator terms at any angle of attack $\alpha$, so the wing never
stalls. Its only drag that grows with angle, for the Rascal, is induced drag,
$C_L^2/(\pi A e)$, which follows the lift: a lift curve that falls past the
stall would also lose drag there, the opposite of a stalled wing.

\paragraph{What we added}
Two optional tables against angle of attack, after JSBSim. A lift table replaces
$C_{L0} + C_{L\alpha}\alpha$; a drag table replaces the zero-lift drag $C_{D0} +
C_{D\alpha}|\alpha|$, and induced and elevator drag are still added. Values are
interpolated linearly and held at the ends, as JSBSim's tables are. JSBSim's
Rascal lift table equals the mission's linear lift up to a peak at 0.23~rad
(13.2$^\circ$), which puts the level stall near 8.3~m/s; its drag table rises
from 0.028 at zero to 1.5 at $\pm90^\circ$. Without tables the model is the C++
one, and its two comparison missions still agree with C++ to rounding
(Appendix~\ref{app:baseline}). Spin and drag from sideslip are not modeled; a
deep stall or large sideslip counts as a failure already.

\paragraph{Does it change a landing?}
ArduPlane SITL flies the Rascal off a runway on surveyed terrain, around a
circuit, and lands it with a 14$^\circ$ flare. With linear lift, the landing
bounced. We flew it three ways: as committed, with the lift table, and with
both tables (Table~\ref{tab:stall}; \texttt{paper/data/stall-landing}). A
repeat of the unmodified mission was byte-identical to the first run, so the
differences between variants are effects of the tables, not run-to-run noise.

The lift table changed the landing by centimetres. Airborne, the angle of
attack never passed 11.2$^\circ$, below the 13.2$^\circ$ stall; only rolling
tail-down on the wheels, above 5~m/s, did it reach 14.5$^\circ$. The drag table
changed more, because it adds drag at every angle, not only past the stall:
touchdown 0.27~m/s slower, a bounce 0.15~m lower, and a rollout within 1.23~m
of the centreline instead of 1.56~m. The bounce itself remains. Touchdown at
about 15~m/s, nearly twice the stall speed, and main wheels ahead of the centre
of gravity, which pitch the nose up on contact, are likely causes; neither is
tested.

\paragraph{What it shows}
This mission exercises the integrated tables and autopilot, but it does not
establish the accuracy of post-stall flight or a multi-agent consequence of
stall. The recorded airborne landing interval stays below the stall angle,
and the larger change comes from drag at small angles. Direct comparison with
the source table evaluations remains a separate check
(Section~\ref{sec:verification}). The lesson is to measure the regime and
state exactly which claim a trial supports.

\section{Multirotor Model}
\label{sec:multirotor}

Each vehicle model reaches the level of an established open simulator
(ArduPilot and PX4 SITL, RotorS): structure from a documented
source, every number's origin stated, and a check against the source
implementation. Going further needs measured data for one real vehicle, which
we do not collect. Instead each model is built so that such data plugs in: a
header on every motion model states its source, what it was validated
against, its valid range, what it leaves out, and what data would take it
further; effects left out are named zero terms in the force sums; and geometry
and coefficients are parameters (rotor axes as vectors, aerodynamics as tables),
so a measured model arrives as data or one function.

Reviewing the inherited multirotor model for this work found three defects,
present in the simulator it was ported from as well. Position is integrated from
a body-frame velocity that starts at zero, while the reported world velocity is
integrated separately, so the two can disagree. Moment arms use the full
three-dimensional rotor offset, so a rotor's height above the centre of gravity
adds leverage, and configured rotor tilt is ignored. Thrust drops to zero only
when a rotor's speed equals the minimum exactly, while its yaw torque remains.
These will be fixed first. Motor lag, rotor drag, and the rolling moment will
follow RotorS \cite{furrer2016rotors} as optional effects. Rotor drag, linear in
airspeed, is small but first order: it sets the velocity dynamics near hover and
is needed to explain accelerometer readings \cite{martin2010accelerometer}. The
inherited quadratic body drag remains as a second term for higher speeds.
RotorS's own motor constants carry no source, so the real-vehicle parameter set
comes from the Crazyflie's measured identification \cite{forster2015crazyflie},
each value cited, beside the inherited defaults kept for the C++ comparison.
Replaying public flights with recorded motor commands \cite{ullah2026nanobench}
would give a stated prediction error; that validation is an extension point. A
controller comes first: no controller yet flies the model closed loop.

\section{Benchmark Tasks}
\label{sec:tasks}

We use three standard tasks, each with published learned results and a
well-established classical method, so every number can be checked against
prior work. Each task is most sensitive to one factor, but all three factors
are varied on all three tasks.

The vehicles follow from that. Point agents come first, set up as in the
published benchmarks, and before any added realism is interpreted, a policy
exported from one pinned benchmark implementation must score the same in
Ripple as in that implementation, with transitions and rewards matched, not
only observations. Published returns come from other versions of the same
tasks, so they serve only as a check on training. The multirotor, with Crazyflie
parameters, is the main realistic vehicle. Learned multi-robot policies that
leave point agents are typically flown on Crazyflie quadrotors: swarm
control \cite{batra2021quadswarm}, flocking \cite{chen2023stgnn}, and
pursuit-evasion \cite{chen2025open}. Current drone learning simulators
model the same vehicle \cite{schuck2026crazyflow,tayal2026mujocodrones},
and outdoor flocking with classical rules flies quadrotors too
\cite{vasarhelyi2018optimized}, so results on it compare directly with that
work. Fixed-wing aircraft, with
constrained kinematics and then 6-DOF dynamics, are the stress case: they
cannot stop, hold a position, or match a neighbour's velocity at any speed,
which is where the classical methods' assumptions break, and we found no
learned versus classical comparison on them. In the particle environments
and VMAS a policy outputs a planar force by default
\cite{lowe2017maddpg,bettini2022vmas}, and VMAS can instead take a target
velocity through a velocity controller. Point agents keep the benchmark's own
force dynamics for the runs that reproduce published results. Beyond those,
policies output a planar velocity: the multirotor follows it directly, and
for aircraft it becomes a heading and a speed held at or above a minimum
airspeed, so a command to stop becomes a loiter. Each task's variant for
aircraft is given below.

\subsection{Cooperative Navigation}
\label{sec:navigation}

$N$ agents must cover $N$ landmarks without colliding, as in the particle
environments' \emph{spread} task \cite{lowe2017maddpg}. The classical solution
is to assign agents to landmarks optimally \cite{kuhn1955hungarian} and fly each
agent to its landmark, or to plan the assignment and trajectories together
\cite{turpin2014capt}. With three agents, current learning algorithms score
within a few percent of one another \cite{papoudakis2021benchmarking}, and the
return also varies with where the agents start. We therefore report, as separate
quantities, the benchmark return as the pinned implementation defines it, the
landmarks occupied at the end, collisions, and the distance flown relative to
the optimal assignment's straight-line cost from the same start, which bounds
travel from below but ignores collisions and is not an optimal return. Aircraft
loiter over their landmark, which counts as covered when an aircraft is within a
fixed radius. A learned policy has been compared with optimal assignment only
with noise-free observations, in its authors' own environment, where it came
close but did not match it \cite{muthusamy2024unlabeled}. Here the main factor
is sensing: assignment computed from each agent's noisy belief, and assignment
by auction over a lossy network, compared with the optimum computed from the
true state.

\subsection{Circle-Crossing Collision Avoidance}
\label{sec:avoidance}

Agents start on a circle and fly to the opposite side, so all of them meet
in the middle. The classical method is reciprocal velocity obstacles (ORCA)
\cite{vandenberg2011orca} and its form for wheeled robots
\cite{alonsomora2010nhorca}; control barrier functions are another
\cite{wang2017barrier}, and a learned version scales them to large teams
\cite{zhang2025gcbf}. Several learned policies are reported to beat ORCA
\cite{chen2017cadrl,long2018towards,everett2021ga3c,fan2020distributed}, but
the comparisons are less clear than they appear. The median gain was small,
with most of it in the hardest cases \cite{chen2017cadrl}; ORCA's radii were
enlarged to stop collisions caused by the discrete time step
\cite{everett2021ga3c}; and a policy using a laser scanner was compared with
an ORCA given its neighbours' true states \cite{long2018towards}. In our
setup both see the same belief. Here the main factor is dynamics. ORCA
assumes an agent can slow down or stop, which a constant-speed aircraft
cannot. Durand shows that aircraft held near constant speed and converging
at small angles settle on parallel tracks without resolving the conflict:
even with $\pm15\%$ speed variation, ORCA failed in more than 20\% of runs
with 10 aircraft, against 10\% with 90 aircraft for his constant-speed
variant \cite{durand2018csorca}. We found no learned versus classical
comparison on fixed-wing aircraft. We run symmetric and perturbed circles and
pair swaps; aircraft fly a holding pattern at the goal. We measure success,
collisions, deadlocks, extra time, and closest approach, at the median and in
the worst cases (the upper percentiles for extra time, the lower ones for
closest approach).

\subsection{Flocking with Limited Communication}
\label{sec:flocking}

Agents start with random velocities and must align and stay together
without colliding, communicating only with neighbours in range. The
classical methods are Reynolds' rules \cite{reynolds1987flocks} and
Olfati-Saber's algorithms \cite{olfatisaber2006flocking}; a version with
parameters evolved in a simulator with delay and noise flew 30 drones
outdoors \cite{vasarhelyi2018optimized}. Tolstaya et al.\ trained a graph
neural network to imitate a centralized controller, passing neighbours'
information along over several hops. It beat a local controller at a short
communication range, where that multi-hop information matters most, and lost
to it at a longer one, which the authors suggest may come from how the
network's inputs were built \cite{tolstaya2020gnn}. Lost and late messages
degrade multi-hop information, so here the main factor is communication, and
we expect loss and delay to change where the learned controller's advantage
holds. Fixed-wing
aircraft cannot hover, so they flock around a moving reference point. We
measure velocity alignment, the number of separate groups, closest approach,
and messages sent.

\section{Training and Evaluation Protocol}
\label{sec:learning}

\paragraph{Training elsewhere, evaluating here}
Ripple has no training code. Policies are trained with existing libraries
\cite{yu2022mappo,bettini2024benchmarl} in fast simulators
\cite{bettini2022vmas,rutherford2023jaxmarl,terry2021pettingzoo}, exported,
and run inside Ripple as an autonomy plugin. The question is not whether
Ripple trains faster than a GPU simulator, but whether a policy trained in a
simple world still ranks where it did once the world is more realistic. To
train at the realistic setting, an outside learner steps Ripple through a
standard multi-agent interface \cite{terry2021pettingzoo}; how fast that
runs has not been measured yet, and it is the first thing to measure.
Learned and classical policies send the same command to the same controllers
(a planar force for point agents in the benchmark runs, a velocity for the
multirotor, and heading, speed, and altitude for aircraft) and read the same
belief. Each task has one observation
definition (frames, scaling, neighbour encoding, decision rate), and a parity
test checks it against the training simulator, since an unnoticed mismatch
would invalidate every result.

\paragraph{Training conditions}
Each learned method is trained three ways: at the benchmark's setting, at
the realistic setting, and with the setting randomized during training.
Comparing the three tells a policy trained in the wrong place apart from a
method that is fragile. Classical methods get the same tuning budget, counted
in evaluations, at the same setting. We also report them tuned at the
benchmark's setting and left unchanged, which matches the first learned
condition.

\paragraph{Statistics}
Each learned configuration uses ten training seeds. We report interquartile
means with stratified bootstrap confidence intervals
\cite{agarwal2021precipice,gorsane2022evaluation}. Learned and classical
policies run on exactly the same evaluation episodes, which determinism
allows. Whether the ranking holds is measured by the rank correlation between
the ranking at each level and at the benchmark's setting, and by counting
ranking reversals, as Kadian et al.\ do between simulation and reality
\cite{kadian2020sim2real}. Policies trained with $N$ agents are also tested
with $2N$ and $4N$. Table~\ref{tab:matrix} lists the design.

\section{Discussion}
\label{sec:discussion}

\subsection{What Makes an Integration Useful?}

An integration is useful when it makes an experiment possible and there is
enough evidence to interpret the results: agreement with an external source,
known physical limits, and measured run cost. It does not need to change a
ranking. An impressive trajectory or a changed ranking also does not replace
checking that the imported model still behaves as intended.

So the work can proceed one model at a time, each adding a level to the
dynamics factor of Section~\ref{sec:learning}. The coordination results
still need held-out layouts, team sizes, and opponents, and runs with
communication removed to check that a policy actually uses it
\cite{ellis2023smacv2}.

\subsection{Limits}

No learned policy has yet been trained or evaluated in Ripple, the network
model has no delay, and no controller yet flies the multirotor, the main
realistic vehicle. No model is yet checked against a vehicle's
measured flight data; the stall tables carry JSBSim's Rascal values, which
their own README calls pre-alpha. The stall result is one mission, one
aircraft, and one autopilot configuration, on one machine; its
byte-repeatability with ArduPilot is shown there and not across machines or
ArduPilot versions. Effects that are not modeled, such as spin and propeller
wash over a wing, bound what the experiments can test.
Agreement of the base system with C++ SCRIMMAGE is established for the models
and configurations in Appendix~\ref{app:baseline}; extensions require
their own comparisons.

\section{Agreement with C++ SCRIMMAGE}
\label{app:baseline}

Ripple began as a port of SCRIMMAGE, so its starting point is checked against
the C++ simulator. Both run the same mission files, and we compare where every
agent went, what each agent believed, what its sensors reported, what each
plugin commanded, and when every message arrived.
\begin{itemize}
\item All 14 hand-written missions and 100 randomly generated scenarios agree,
to $2.4\times10^{-10}$~m at worst and usually to about $10^{-14}$~m, which is
floating-point rounding.
\item The comparison catches all 12 planted porting bugs, such as a controller
gain 1\% too high or a message one tick late. Two message bugs leave
trajectories unchanged and are caught only by the trace.
\item Eight of ten runs of up to 1{,}000~s agree throughout; the other two end
about 0.2~mm and $8\times10^{-9}$~m apart, and perturbation controls suggest
numerical sensitivity.
\item Seven NoisyContacts error distributions show no difference at the
corrected significance threshold (smallest $p = 0.031$ against 0.0071).
\item Every other difference is a C++ defect that Ripple fixes or a documented
choice (Table~\ref{tab:differences}).
\end{itemize}
The results come from one release run of the checks from a clean checkout
(Appendix~\ref{app:reproduction}); \texttt{paper/data/release.json} records the
hash of the source that ran and the C++ commits, \texttt{4bdf41fb0}
(\texttt{Ubuntu-24.04}) and \texttt{1c8595b91} (\texttt{benchmarking-edits}).

\paragraph{Builds}
Each C++ branch is built from a \texttt{git archive} in the unmodified
upstream dependency image (\texttt{linux/amd64}, GCC~13.3), headless and
single-threaded. \texttt{Ubuntu-24.04} is the unmodified reference.
\texttt{benchmarking-edits} adds opt-in instrumentation and three fixes that
Ripple shares: the substep order (below); AircraftPIDController using its
given timestep, with a lower default altitude derivative gain
(\texttt{5777aeea1}); and FixedWing6DOF and Multirotor computing forces at
every RK4 stage instead of only from the start-of-step state
(\texttt{1c8595b91}, \texttt{paper/data/rk4-loads}). Every mission also runs on
the unmodified build, and instrumentation must leave frames and summaries
byte-identical.

\paragraph{Trace}
Set with \texttt{SCRIMMAGE\_TRACE} in C++ and \texttt{-{}-trace} in Ripple, it
records every message delivery (tick, network, topic, sender, receiver, and the
entities in lifecycle and collision events), every published sensor state and
covariance, each entity's belief, and every output the next plugin reads.
Other message contents, such as auction bids, are compared by delivery only.

\paragraph{Criteria}
States, beliefs, and readings must agree within $10^{-8}$~m, $10^{-8}$~m/s,
$10^{-9}$~rad, and $10^{-9}$~rad/s; plugin outputs within $10^{-8}$;
covariances within $10^{-9}$; summaries within $10^{-6}$. Deliveries must
match exactly and in order. The position limit is 27 times the largest
difference measured in a passing run when it was set; it replaced a 0.01~m
limit that let a planted sub-micrometre bug through.

\paragraph{Random draws}
The C++ standard leaves the default random engine and the normal
distribution's algorithm to each library, and GCC's differs from the LLVM
behavior Ripple reproduces. With \texttt{SCRIMMAGE\_LIBCXX\_SPAWN\_RANDOM} the
C++ branch draws spawns from \texttt{std::minstd\_rand} with Ripple's normal
algorithm: the randomized mission then agrees to $1.4\times10^{-14}$~m instead
of differing by up to 8.42~m. Ripple gives each sensor its own random stream,
so sensor noise is compared with fixed-bias fixtures and by distribution.

\paragraph{Long runs}
Ten generated scenarios run for up to 1{,}000~s. For one that diverges, a
control perturbs Ripple alone (one unit in the last place on initial roll,
speeds, and turn radii, and controller gains scaled by $1+10^{-12}$) and
measures when Ripple diverges from itself. In \texttt{generated-000} an
aircraft settles into a sustained pitch oscillation; C++ and Ripple separate
after 28.8~s and the control after 26.8~s, both ending about
$2\times10^{-4}$~m away. In \texttt{generated-007} C++ and Ripple separate
after 76.4~s, the control already after 14.4~s (Table~\ref{tab:long}). This
suggests numerical sensitivity; it does not rule out a small implementation
difference.

\paragraph{Summaries}
A differing summary passes only if entity and collision counts match exactly
and Ripple's metrics messages reproduce the C++ summary under the C++ scoring
rule and Ripple's summary under its documented rule
(\texttt{reference/metrics\_model.py}). The only exclusion: first-step trace
records of entities C++ destroys before the first step, which C++ still runs
for that step; they are counted.

\paragraph{The substep correction}
A mission can split each tick into substeps so that vehicle physics runs
finer than decisions. From its first public commit in 2017, SCRIMMAGE ran each
substep as the controllers and then the motion model, a cascade in which the
controller sees the state the previous substep wrote. The commit adding GPU
support (\texttt{c0a9f42b2}, December 2025) ran all controller substeps before
any motion, with no stated reason. With more than one substep, every
controller call in a tick then sees the same state and goal, the motion model
flies only the last command, and a PID controller's derivative term is zero on
calls whose setpoint and measurement are unchanged. With one substep the two
orders are identical, so comparison with the current C++ could not reveal it.
The comparison branch (\texttt{7129e47f5}) restores the interleaved order and
Ripple follows it. The unmodified and fixed C++ write identical output on all
nine curated single-substep missions that use no other corrected plugin, and
the two substep missions agree with the fixed C++ to $4.8\times10^{-14}$~m.

\paragraph{Coverage and limits}
Compared: SimpleAircraft, FixedWing6DOF, Multirotor, and SingleIntegrator with
their controllers; Straight; AuctionAssign's message timing; NoisyState and
NoisyContacts; SimpleCollision, GroundCollision, and Boundary; Global, Local,
and SphereNetwork; SimpleCollisionMetrics; substeps, update rates, and
scheduled and randomized spawning. Agreement covers these models in the tested
configurations, not the whole C++ plugin catalog. Results agree to rounding,
not bit for bit, because the two call different math libraries. NoisyState
noise is not tested by distribution, and NoisyContacts only by seven marginal
distributions in one fixture.

\section{Determinism}
\label{app:self}

Ripple's output is byte-identical across 1, 2, and 8 workers, with and without
recording and tracing, and whether a scenario comes from XML, YAML, or Rust
code. Workers own separate entities, every phase finishes before the next
starts, and random draws are tied to entities and plugins rather than workers.
Built for Linux/amd64 instead of macOS/arm64, events and summaries stay
identical in all 56 runs checked and trajectories differ by at most
$2.4\times10^{-12}$~m, because each system's math library rounds differently
(\texttt{reference/platform\_check.py}).

\section{Scaling}
\label{app:scaling}

Two costs in SCRIMMAGE's design grow with the square of the team size: finding
which agents are near each other, and deciding which messages reach which
plugins. Ripple removes both inside the engine without changing any output.

\paragraph{Finding nearby agents}
SCRIMMAGE's SimpleCollision compares every ordered pair of agents. In Ripple a
plugin asks the engine once for the agents within a range, or for every close
pair, and the mission chooses how the engine answers: a scan of every agent
(the default, and the only method for XML missions) or a grid of vertical
columns of width $w$. The grid supplies only candidates; each gets the scan's
exact distance test, and survivors come back in entity order, so the answer
and its order never change. The grid is built after motion and rebuilt before
interactions, networks, and metrics if anything moved. SimpleCollision now
consumes close pairs in the order its old double loop visited them, so events
and survivors are unchanged. The determinism check runs every mission and
three crowded ones (up to 2{,}048 agents and 795 collisions) with the scan and
with grids from 0.7 to 1{,}000~m: frames, summaries, and events are
byte-identical. With 4{,}096 spread-out agents a step takes 9.0~ms with the
scan and 3.8~ms with 5~m cells (Table~\ref{tab:spatial}); with 256 agents the
grid is 9\% slower.

\paragraph{Delivering messages}
C++ checks each message against every subscriber to its topic, so when every
agent publishes on a topic every agent subscribes to, as NoisyState does on
LocalNetwork, that is $n^2$ checks per tick. Ripple indexes each published
channel's subscribers per routing phase, and a network that delivers only
within the sender's agent (LocalNetwork) routes against that agent's
subscribers alone. Every link a network decides is decided with the same
inputs and in the same order as in C++, and the C++ comparison requires all
6{,}132 traced deliveries to match. With 4{,}096 agents running NoisyState a
step takes 9.4~ms in Ripple against 378~ms in C++ (Table~\ref{tab:messages}).

\paragraph{Cost against C++}
On five timing workloads on one Apple M2 Pro, Ripple on one core is 1.04 to
1.6 times faster than single-threaded C++ where the two produce identical
output, and uses 2.1 to 6.3 times less memory on every workload
(\texttt{paper/data/speed-cpp-container/},
\texttt{paper/data/speed-cpp-native/}). C++'s own multi-threaded mode
deadlocked in 9 of 219 runs and is not used as the baseline.
