\section{Introduction}

SCRIMMAGE provides a plugin-based environment for multi-agent robotics
experiments \cite{demarco2018}. Since its publication, the field has moved
toward robots that share maps and plans over limited links, planners that
evaluate many alternatives on accelerated hardware, and teams that serve
continuing streams of tasks. This paper asks which of these developments
change the experiments a multi-agent robotics testbed should support, and what
evidence would justify building that support.

We focus on three research questions, each paired with the capability it
would need and an experiment that could show whether that capability matters:
\begin{description}
  \item[RQ1:] When does sharing information improve team performance?
  \item[RQ2:] When does more planning computation improve the outcome?
  \item[RQ3:] When does a larger team stop completing more work?
\end{description}

Answering these requires a testbed whose results can be trusted, so that a
different outcome can be attributed to the algorithm rather than to its setup.
We therefore first establish a baseline: SCRIMMAGE-RS, a Rust implementation
that retains SCRIMMAGE's simulation structure. We check that it behaves like
SCRIMMAGE, that experiments are easier to set up and repeat, and that it runs
at comparable cost (Section~\ref{sec:baseline}).

\section{SCRIMMAGE and What Has Changed}
\label{sec:original}
\label{sec:background}

SCRIMMAGE was built to simulate many interacting aerial robots without
requiring expensive physics for every experiment \cite{demarco2018}.
Researchers could replace motion, sensor, network, and behavior models while
keeping the same simulator. Its original paper already described deterministic
execution, batch runs, cluster deployment, and ROS, MOOS, and OpenAI Gym
connections. In its predator/prey experiment, repeatedly switching to the
nearest prey performed worse than committing to a target: the pursuers could
be distracted just before a capture. That is the kind of behavioral result
a testbed should make easy to investigate.

Table~\ref{tab:timeline} connects selected developments since then to the
experiments they motivate. Many new coordination algorithms fit SCRIMMAGE's
existing roles for sensors, networks, controllers, and metrics without
changing the engine. A core upgrade is justified only when an experiment needs
a shared capability that these interfaces cannot express clearly, or when the
existing execution model imposes a measured cost. We distinguish these cases
from reusable experiment models throughout.

\section{A Validated Baseline}
\label{sec:baseline}
\label{sec:upgrades}

This section describes SCRIMMAGE-RS and summarizes three checks: that it
behaves like SCRIMMAGE, that an experiment is easier to build in it, and what
it costs to run. The behavior checks were repeated after adding the
estimation stage (Section~\ref{sec:estimation}), and the cost measurements
include it. The details are in the appendices.

\subsection{SCRIMMAGE-RS}

Each entity owns its autonomy, controllers, motion model, and sensors.
Interactions, networks, and metrics operate on the world. An autonomy chooses
a desired command; controllers turn it into motion-model inputs; the motion
model advances the state. Sensors then produce observations, interactions
apply effects such as collisions, networks deliver messages, and metrics
update scores. The engine finishes each phase before starting the next, even
when entities run on different CPU workers.

User plugins live in a workspace crate and register with the same
\texttt{scrimmage} executable as the stock models. A plugin owns its parameters
and state; the engine handles scheduling and message delivery. XML and YAML
missions load into one typed scenario; YAML adds shared entity templates and
parameter sweeps, and the simulator checks the scenario and plugin parameters
before running. A run saves trajectories, events, scores, and a manifest, with
Rerun for recorded visualization. Sweeps write one result row per case and can
be split into local processes or Slurm array shards, although cluster
submission has so far been tested with a mock scheduler.

\subsection{Behavior}
\label{sec:parity}

Does SCRIMMAGE-RS behave like SCRIMMAGE? We ran the same mission files in both
and compared not only where every agent went, but also what each agent
believed, what its sensors reported, what each plugin commanded, and when every
message arrived (Appendix~\ref{app:parity}).
\begin{itemize}
\item \emph{They agree.} All 14 hand-written missions and 100 randomly
generated scenarios match. Positions agree to under a nanometre, usually to
about $10^{-14}$~m, which is floating-point rounding.
\item \emph{The comparison is strict enough to catch real mistakes.} To test
it, we introduced 12 small, realistic errors into a copy of the Rust code, such
as a controller gain 1\% too high or a message arriving one step late. The
comparison flagged every one.
\item \emph{Long runs mostly hold.} Nine of ten runs of up to 1{,}000~s
match throughout. The remaining run ends about 0.2~mm apart; perturbation
experiments suggest numerical sensitivity.
\item \emph{Every other difference is a C++ bug that Rust fixes or a
deliberate choice,} such as C++ scoring late-spawning teams as NaN; all are
listed in Table~\ref{tab:differences}.
\end{itemize}
This holds for the models and configurations we tested
(Appendix~\ref{app:coverage}), not the whole C++ plugin catalog.

\subsection{A Regression in the Reference}
\label{sec:substeps}

Matching a reference also means inheriting its mistakes. Reading the C++
history turned up one that output comparison could not, because both
simulators did the same thing.

\paragraph{The original design}
A mission can split each tick into shorter substeps, so that vehicle physics
runs at a finer time step than decisions and sensing. From its first public
commit in 2017 until December 2025, SCRIMMAGE ran each substep as the
controllers followed by the motion model. This is a cascade: a slow outer loop
(autonomy) sets goals, and a fast inner loop (controller and physics) tracks
them, with the controller seeing the state the previous substep wrote. JSBSim
likewise runs its flight-control system before each frame's dynamics
\cite{berndt2004jsbsim}, and Isaac Lab runs actuator models on every physics
step while holding a slower policy's action \cite{mittal2025isaaclab}.

\paragraph{What changed and why it matters}
The commit adding GPU support ran every controller substep before any motion,
so that one GPU call could advance all substeps together; it gives no reason
for the new order. With more than one substep, every controller call in a tick
then sees the same state and the same goal, and the motion model flies only the
last call's command. The controller gets no feedback within the tick, and a PID
controller's derivative term, the change in error divided by the time step, is
zero on every call whose setpoint and measurement are unchanged, so it loses its
damping. With one substep
the two orders are identical, which is why most missions were unaffected and
why comparison against the current C++ could not reveal it.

\paragraph{The fix}
The C++ comparison branch restores the interleaved order, and SCRIMMAGE-RS
follows it: controllers and motion alternate at each substep, while autonomy,
sensing, communication, and interactions keep the outer tick. SCRIMMAGE-RS
controllers read belief, so when own-state belief comes from the perfect
measurement it is refreshed after each motion substep, as the C++ controllers
read truth unless a sensor provides belief. Sensor-based estimates keep their
own timing, so more substeps do not mean fresher observations, or finer
collision checks. Every mission and workload with one substep produced
byte-identical output before and after the change. The two substep missions
agree with the fixed C++ to $5\times10^{-14}$~m, and one long run with two
substeps now agrees with C++ throughout. Appendix~\ref{app:substeps} gives the
commits, the verification, and the cost. The fix changes only the schedule; the
numerical approximations inside the retained motion models remain.

Both give the same answer: the chaser catches the target at 26 and 30~m/s, at

branch. Appendix~\ref{app:rq2} gives the details, and \texttt{paper/rq2/} holds
both versions and the commands.

\subsection{Cost}
\label{sec:performance}

We ran the same five missions in both simulators on one laptop (an Apple M2
Pro): aircraft flying straight, the same with finer physics steps, aircraft
with noisy sensors, a stream of new aircraft that can collide, and a large
spread-out group checked for collisions every step. Each ran at several sizes,
up to 2{,}048 aircraft (Appendix~\ref{app:performance}).
\begin{itemize}
\item \emph{Rust is faster on one processor core,} by 1.05 to 1.7 times. We
compare speed only on the two missions where both simulators produce identical
results.
\item \emph{Rust uses much less memory,} 2.0 to 6.0 times less on every mission
and size.
\item \emph{Collision checking was the limit for large teams, and spatial
queries remove it.} Both simulators compared every pair of aircraft, so the
cost grew with the square of the team size: doubling from 1{,}024 to 2{,}048
aircraft made Rust's collision mission more than three times slower. With the
spatial queries of Section~\ref{sec:spatial}, a step with 4{,}096 spread-out
aircraft takes 10.2~ms by default and 5.0~ms with the optional grid, against
19.1~ms before: 1.9 and 3.8 times faster, with identical output.
\item \emph{Message routing is the next limit, in both simulators.} Deciding
which messages reach which plugins takes one check per publisher--subscriber
pair, so a sensor on every agent that every agent listens to costs $n^2$ checks
per tick. With 4{,}096 aircraft each running an own-state sensor, a step took
388~ms in both C++ and Rust. Routing by index (Section~\ref{sec:messages}) cuts
that to 9.7~ms, 40 times faster, with identical output.
\item \emph{Extra cores help only when there is enough work.} Rust on eight
cores ran the sensor mission 3.2 times faster than on one, but the simplest
missions ran slower: handing out work to the cores every step costs more than
the work itself.
\item \emph{C++'s multi-core mode is unreliable.} It froze in 14 of 224 runs,
gave different answers to the same run when sensors were involved, and was
usually slower than running C++ on one core. We compare against single-core
C++.
\end{itemize}
We measured both in a Linux container and directly on macOS; the findings hold
in both.

\section{Separating Measurement from Belief}
\label{sec:estimation}

The first extension changes how a robot comes to know its own state and its
surroundings. In SCRIMMAGE a sensor can write the robot's belief directly, any
sensor can overwrite it, and a planner may read belief, subscribe to a sensor's
message itself, or fall back to truth when no estimate exists. Every
experiment that involves imperfect information has to wire these pieces by
hand. SCRIMMAGE-RS now has an explicit estimation stage: sensors produce
measurements, estimators own belief, and autonomy and controllers read only
that belief. Table~\ref{tab:estimation} shows what this changes for a
developer.

\begin{table*}[t]
\centering
\small
\caption{Common tasks before and after the estimation stage.}
\label{tab:estimation}
\begin{tabularx}{\textwidth}{@{}P{0.22\textwidth}XX@{}}
\toprule
Task & SCRIMMAGE & With the estimation stage \\
\midrule
Choose which sensor feeds the robot's state & Implicit: any sensor can overwrite belief, and the last writer in a step wins & Named in the mission and checked before the run \\
Give a planner its state & The planner reads belief, subscribes to a sensor's topic itself, or falls back to truth & The planner reads belief, always \\
Swap the localization method & Edit every planner that selected its own source & Change the localizer; planners are untouched \\
Configure error & Sensor noise, motion disturbance, and wiring are set in separate places & Each source of error is set once, at its owner \\
Keep decisions from using hidden truth & Not enforced: decisions can read the true state of every entity & Decisions receive belief only \\
Measure how wrong the robot was & Worked out by hand after the run & Truth and belief are recorded separately; recording measurements is future work \\
\bottomrule
\end{tabularx}
\end{table*}

\paragraph{Two estimators, one belief}
Belief has two parts, each with one owner. \emph{Localization} answers
``where am I?'': it turns navigation measurements (GPS, IMU) and the commands
the robot issued into its estimated state. \emph{Tracking} answers ``what is
around me?'': it turns contact measurements (radar, camera) into the contacts
the robot knows about, using the pose localization just produced. Each can be
replaced without touching the other or any planner. Sensors and evaluation
keep access to physical truth; estimators and decisions do not.

\paragraph{What changes in a tick}
The stage runs after sensors and message delivery and before metrics,
localization first, and keeps the existing order of every other phase. With a
0.1~s timestep:
\begin{enumerate}
\item \emph{Decide at time 0.0.} Autonomy and controllers read the belief for
time 0.0 and produce the inputs the motion model will use.
\item \emph{Advance to 0.1.} The motion model advances physical truth; sensors
sample the result, interactions apply their effects, and networks deliver the
messages due.
\item \emph{Form belief for 0.1.} Localization, then tracking, update belief
from the completed interval and the information now available.
\item \emph{Decide at time 0.1,} using that belief.
\end{enumerate}
Estimation adds computation to each tick, not simulated delay; modeling
processing delay would be a separate, explicit choice.

\paragraph{Pass-through first, prediction next}
The first implementation copies measurements into belief. With perfect, current
measurements, which simple missions use by default, belief equals truth at
each decision for every entity already observed (an entity that has just
appeared is known from the next measurement). Existing missions are therefore
unaffected: every mission, at one, two, and eight workers, reproduced the
previous revision's output byte for byte, and all 13 C++ comparisons still
pass (Appendix~\ref{app:refactors}). The stage runs inside the existing
per-entity delivery step, so it adds work but no extra hand-off between
threads: up to 8\% more stepping time on our timing workloads, most for many
light agents, where there is little other work per tick (collision workloads
ran faster, a side effect of the larger entity record on memory access; data in
\texttt{paper/data/estimation-cost/}). A predictive
localizer then occupies the same stage: it advances the previous belief using
the commands the robot issued and its own motion model, and corrects that
prediction with measurements. Because the physical response, the estimator's
assumed response, and measurement error are configured separately, an
experiment can vary each on its own. In the worked example
(\texttt{crates/starter}), a robot commanded at 10~m/s achieves 8~m/s and gets
an exact position fix every 5~s. With a localizer that assumes 10~m/s, the
position error grows by 2~m per second on straight segments, and the largest
error sampled at the end of a step is 9.8~m (the prediction each fix replaces
is 10~m off); with one that assumes 8~m/s, the estimated
position matches the true one. The starter crate's tests check these numbers. Acting on the wrong belief, the robot turns early at every corner
of its square route and strays up to 22~m from a robot with perfect
localization.

\section{Removing Inherited Scaling Limits}
\label{sec:scaling}

Two costs in SCRIMMAGE's design grow with the square of the team size: finding
which agents are near each other, and deciding which messages reach which
plugins. Both are hidden inside the engine, and both come to dominate a step
as teams grow, in C++ as in the Rust port, which kept the same design. They are
properties of the original design, not porting errors. We remove each inside
the engine, without changing any plugin's results, so experiments with larger
teams become practical, which RQ1 and RQ3 need.

\subsection{Finding Nearby Agents}
\label{sec:spatial}

Many models ask the same question: which agents are within some distance of a
point? Collision detection asks it with a few metres, a short-range radio with
a kilometre, a range-limited sensor with its detection range. SCRIMMAGE's
SimpleCollision answers by comparing every ordered pair of agents, so each pair
twice; its R-tree is used only to place agents at spawn time. Its collision
mission became 3.8 to 9.3 times slower from 1{,}024 to 2{,}048 aircraft
(Appendix~\ref{app:performance}). The retained Rust plugin compared each pair
once, and its cost still grew with the square of the team size: at 1{,}024
agents it took 58\% of each step, at 4{,}096 agents 79\%. SCRIMMAGE-RS moves this question into the engine,
so each plugin asks it once and the engine decides how to answer. The result
is large and changes no output: with 4{,}096 spread-out agents, a whole step
fell from 19.1~ms to 10.2~ms with the default method and to 5.0~ms with the
optional grid, 3.8 times faster (Table~\ref{tab:spatial}).

\paragraph{One question, two answers}
World plugins (sensors, networks, and metrics) call
\texttt{within(position, range)} on the true contacts. It returns every
contact whose distance from \texttt{position} is less than \texttt{range},
in the contacts' order. It does not filter: the caller itself, and contacts
already removed, are included, and each plugin applies its own rules.
Interactions, which change entities, ask the same question by entity index,
and can also ask for every close pair, \texttt{pairs\_within(range)}, in the
order a loop over all pairs would visit them.
The mission chooses how the engine answers, once for the whole run:
\begin{itemize}
\item \emph{Scan} (the default) tests every contact. It is the reference
answer, and it keeps the C++ timing comparison like-for-like.
\item \emph{Grid} (\texttt{spatial\_lookup: \{method: grid, cell\_width\_m:
$w$\}}) tests only contacts in nearby cells.
\end{itemize}
Plugin code is the same either way; no plugin knows which method answered.
XML missions always use the scan.

\paragraph{How the grid works}
After all motion substeps, the engine gives each agent an integer cell,
$(\lfloor x/w \rfloor, \lfloor y/w \rfloor, \lfloor z/w \rfloor)$, and adds
it to a hash map from its vertical $(x, y)$ column to the agents in that
column. Only occupied columns appear, so memory is one short entry per agent,
independent of the size of the map. A query with
range $r$ covers the cells overlapping a box of half-width $r$ around its
position, padded by a relative $10^{-9}$ so that rounding cannot exclude a
neighbour (typically nine columns when $r \le w$). The cells supply only
\emph{candidates}.
Every candidate then gets the scan's exact test, $\|p - q\| < r$
computed the same way, and the survivors are returned in entity order. The
grid can therefore only drop agents the exact test would reject, and never
changes the answer or its order; it changes only how many agents are tested.
If any position is not finite or too large for an integer cell, the tick uses
the scan. A query also scans when looking up its columns would cost more than
testing every agent; we measured one column lookup at about 30 distance tests.
Keying by column keeps lookups few when agents are spread out horizontally,
but a query tests every agent in its columns at any height, so many agents
stacked above one spot would bring back the every-pair cost.

\paragraph{When the grid is built}
After motion, before sensors, which share it without locks because it is built
before the parallel sensor phase. An interaction may move entities, so the
engine checks the index against current positions before each interaction and
again before networks and metrics, and rebuilds it if anything moved; the check
is one pass over the agents. Every query therefore sees current positions, and
the scan and the grid always answer from the same ones. SCRIMMAGE instead
builds its R-tree when entities are generated, before motion, so a plugin that
queries it later in the tick compares a moved agent with where the others
were. The index holds positions only: whether an agent is still alive is read
live by the plugin, because one collision can disable later ones.

\paragraph{Collision detection as the first user}
SimpleCollision previously visited every pair $(i, j)$ with $j > i$ in entity
order, skipped pairs with a disabled agent, and disabled both agents of each
pair closer than the collision range. The order matters: in a chain of three
overlapping agents, the pair visited first decides which agent survives. The
rewritten plugin iterates over \texttt{pairs\_within}: for each agent $i$ in
order, the engine finds its neighbours, keeps those with $j > i$, and yields
them in ascending order, as the plugin consumes them. That is exactly the old
sequence with the pairs that could never collide removed, so events and
survivors are unchanged. With the scan, the loop is the old double loop over a
compact list of positions. Placement at spawn time, which uses an
inclusive range and an altitude-only option, still scans, so spawn retries and
random draws are unchanged too.

\paragraph{What this preserves}
We compared the previous revision against the new scan and the grid on 37
missions (\texttt{paper/data/spatial-lookup/equivalence.py} and its report):
every mission file in the repository, the timing workloads at both sizes,
including spawning with collisions (153 collisions at 512 agents), and three
crowded missions (512 to 2{,}048 agents, 235 to 795 collisions). Frames,
summaries, and events were byte-identical with the scan at one, two, and eight
workers and with grids from 0.7 to 1{,}000~m. Tests cover the three-agent chain
with ids created out of order, an interaction that moves one agent onto another
before SimpleCollision (the collision is found in the same step), points
exactly at the range, on cell faces, and at negative coordinates, contacts held
in a different order from their ids, and non-finite positions and ranges. The
grid tests use enough agents that the grid, not its fallback, answers. In the
timing runs below, every variant with a collision check also wrote identical
output, up to 4{,}096 agents. The full C++ campaign, rerun after the change, is unchanged:
all 13 missions and 100 generated scenarios pass, and all 12 planted bugs are
caught.
Decisions cannot use the grid: autonomy and controllers see only belief, and
can ask the same \texttt{within} question of their own known contacts, which
the engine answers by scanning that list.

\paragraph{Cost}
Table~\ref{tab:spatial} times perf.py's collision mission, alternating the
previous revision's every-pair loop, the scan, and the grid
(\texttt{paper/data/spatial-lookup/}). With 4{,}096 spread-out agents, a whole
step took 19.1~ms before, 10.2~ms with the scan, and 5.0~ms with 5~m cells: 1.9
and 3.8 times faster. With 2{,}048 agents the grid was 2.5 times faster, and
with 1{,}024, 1.5 times. The scan reads positions from a compact list and
touches entity records only for pairs in range. Subtracting a run without
SimpleCollision estimates the check's own cost at 4{,}096 agents: about 15~ms
per step before, 6~ms with the scan, and 0.9~ms with the grid. It is only an
estimate, because that run removes no agents and may place spawns differently.
Larger cells were slightly faster (4.7~ms per step with 50~m cells), because a
lookup costs more than the few extra distance tests an occupied cell adds.
The grid can be slightly slower than the scan. With 256 agents its queries fall
back to the scan, and building it makes the step 9\% slower (0.23 against
0.21~ms). In the crowded 1{,}024-agent case the step is 4\% slower, and with a
50~m range and 5~m cells, 2\% slower; 50~m cells were 7\% faster than the scan
there. Other workloads are unchanged within 3\% (perf.py). The C++ comparison
in Section~\ref{sec:performance} was measured before this change.

\subsection{Delivering Messages}
\label{sec:messages}

Each tick, a network decides which published messages reach which subscribers.
SCRIMMAGE asks the network one question per link: can this publisher reach this
subscriber, and does the message get through? C++ keeps each topic's publishers
and subscribers in lists, so a message is checked against every subscriber to
its topic, and LocalNetwork, which delivers only within one agent, answers each
check by comparing the two plugins' parent entities. When every agent publishes
on a topic that every agent subscribes to, that is $n^2$ checks per tick to
deliver $n$ messages. The own-state sensor NoisyState does exactly this: every
agent publishes its reading on LocalNetwork, and every agent's Straight
autonomy subscribes to it. (In SCRIMMAGE-RS the reading reaches belief through
the estimation stage, and Straight discards the message; NoisyState keeps
publishing it only so that delivered messages still match C++. It is a
convenient built-in source of all-agent traffic, which auctions, shared maps,
and position broadcasts also produce.) The Rust port delivered the same messages to each
subscriber in the same order (the C++ comparison checks this), but found the
links differently: for each message it visited every plugin's mailbox, several
per agent, and looked up that mailbox's subscriptions by channel name. It
therefore also checked messages that nobody subscribed to, which C++ skips.

\paragraph{How large the cost is}
Table~\ref{tab:messages} times perf.py's aircraft with and without NoisyState
in native C++ and in Rust (\texttt{paper/data/message-routing/}). The
difference is everything the sensor adds (its noise, readings, estimation, and
messages), and it grows with the square of the team: 0.46, 6.3, 94, and 385~ms
per step in C++ at 128, 512, 2{,}048, and 4{,}096 agents, and 0.45, 6.1, 93,
and 385~ms in Rust, within about 3\% of each other, against 2.9 to 3.7~ms for
the rest of a 4{,}096-agent step. Profiles of the 2{,}048-agent case (saved
beside the timings) put almost all of that in routing: in C++, in
\texttt{LocalNetwork::is\_reachable} and the \texttt{EntityPlugin::parent}
calls it makes; in Rust, in \texttt{NetworkContext::route} and its
channel-name comparisons. The two arrive at the same cost by different routes.
C++ checks only a topic's subscribers, but copies two reference-counted
pointers per check; Rust checked every mailbox, but each check was cheaper.
Spawning had the same cost, because each new agent publishes an event: a
one-step Rust run with 2{,}048 agents took 70~ms before routing by index and
14~ms after, and with 4{,}096 agents 249 and 26~ms.

\paragraph{Routing by index}
Each routing phase, the engine indexes the mailboxes subscribed to each channel
published that phase, in mailbox order, with the message type each expects, so
a message visits only its subscribers, as in C++. A network that delivers only
within the sender's own agent says so by calling \texttt{route\_within\_entity}
instead of \texttt{route}; LocalNetwork does. The index is then kept per agent,
so each message sees only its own agent's subscribers, and a message from a
world plugin, which has no agent, sees none. LocalNetwork's rule is unchanged;
it moved from the plugin into the call it makes. The index is built only in
phases that have messages, so a network with nothing to route costs nothing
extra, and queued deliveries find their receivers in one map instead of
searching every mailbox. Every link a
network decides is decided with the same inputs and in the same order, so
deliveries, random draws, and output are unchanged. What the index cannot
remove are links that exist: a topic every agent publishes and subscribes to on
a network that can reach every agent (GlobalNetwork, or SphereNetwork in
range) still has $n^2$ links, and each must be decided.

\paragraph{What this preserves}
We ran the previous and the new revision on every mission file in the
repository, perf.py's workloads, and 512 aircraft with NoisyState, at one, two,
and eight workers, with the C++ comparison trace on
(\texttt{paper/data/message-routing/equivalence.py} and its report). All 35
missions wrote byte-identical frames, events, summaries, and traces, which
record every delivery with its network, topic, sender, and receiver in order: up
to 153{,}728 deliveries in one run, including SphereNetwork's missions, whose
loss draws depend on the order in which links are decided. The planted bug that
lets LocalNetwork deliver across agents is now a call to \texttt{route} instead
of \texttt{route\_within\_entity}. The full C++ campaign, rerun on the final
code, is unchanged: all 13 missions and 100 generated scenarios pass, and all 12
planted bugs are caught, this one by the trace comparison in two missions.

\paragraph{Cost}
With routing by index, adding NoisyState costs 0.17, 0.72, 3.0, and 6.8~ms per
step at 128 to 4{,}096 agents, against 0.45, 6.1, 93, and 385~ms before: at
4{,}096 agents a whole step takes 9.7~ms instead of 388~ms in Rust and 388~ms in
C++, 40 times faster (Table~\ref{tab:messages}). What remains grows roughly
linearly; in the new profile no routing function stands out, and the largest
entries are map lookups and memory allocation. Steps without messages are
unchanged. On perf.py's workloads, alternating the two builds five times each,
the sensing workload with 128 aircraft (NoisyContacts and NoisyState on every
aircraft) was 11\% faster on one worker and 34\% faster on eight; the others
were within 5\% either way, the run-to-run noise of those short workloads.

\section{RQ1: When Does Sharing Information Improve Team Performance?}
\label{sec:rq1}
\label{sec:rq4}

\paragraph{What changed}
Kimera-Multi builds consistent maps through peer communication, while RACER
coordinates exploration and workload allocation
\cite{tian2022kimera,zhou2023racer}. These motivate a question beyond adding
radio loss: what information should robots share, and when does its value
outweigh its cost? A comparison is meaningful only if each method receives
the information allowed by the experiment.

\paragraph{What the baseline cannot express}
The retained interface exposes truth contacts to autonomy. Rust separates
owned belief from truth, but a plugin can still read those contacts, and
own-state feedback falls back to truth when no estimate exists. Sensor and
network models alone therefore do not enforce partial observability.

\paragraph{Candidate capability}
The estimation stage of Section~\ref{sec:estimation}, now in place. With
decisions reading only belief, and belief formed from named measurements, an
experiment can control exactly what each robot knows and compare sharing
policies fairly.

\paragraph{Experiment}
Compare local decisions, periodic sharing, and selective sharing on the same
exploration task under a fixed message budget. Measure coverage, duplicated
work, and stale decisions, using ideal information as a separate reference
condition. The upgrade's contribution would be a checkable information
boundary; the scientific result would identify when sharing helps. A simple
target-observation model can address this question without implementing a
visual-SLAM system.

\section{RQ2: When Does More Planning Computation Improve the Outcome?}
\label{sec:rq2}

\paragraph{What changed}
Isaac Gym, VMAS, and Isaac Lab show the importance of accelerated workloads
\cite{makoviychuk2021isaacgym,bettini2022vmas,mittal2025isaaclab}. For this
testbed, the question is whether evaluating more alternatives improves team
outcomes enough to justify the computation. That requires measuring both
planning quality and when a decision becomes available.

\paragraph{What the baseline cannot express}
The retained scheduler calls each entity's autonomy separately and joins the
phase before advancing. A costly call slows wall-clock execution without
making its decision late in simulation time. A plugin can already perform
its own calculations or defer its own output, but shared batches across
entities and consistent decision-delay rules require additional support.

\paragraph{Candidate capability}
An optional shared batch interface and an explicit model of decision
availability. Requests would carry observation times; results would take effect
at defined phase boundaries. Prescribed or recorded delays would support
repeatable experiments without letting GPU completion order determine simulated
behavior.

\paragraph{Experiment}
The planned Burn workload could evaluate batches of candidate trajectories.
First compare CPU and GPU execution of the same calculation, including
packing, transfers, and synchronization. Then vary the planning budget and
modeled decision delay, measuring completion, collisions, and expired
commands. The baseline's cost measurements (Section~\ref{sec:performance})
cover execution time; this experiment asks whether the additional computation
changes the decision that can be made in time. Batched inference or scoring
would not imply GPU physics or a batched-world simulator.

\section{RQ3: When Does a Larger Team Stop Completing More Work?}
\label{sec:rq3}

\paragraph{What changed}
RHCR addresses repeated goals, and RACER balances exploration workloads
\cite{li2021rhcr,zhou2023racer}. These motivate measuring sustained useful
work as demand and team size grow. Faster simulation of more robots does not
establish that a coordination method uses those robots effectively.

\paragraph{What the baseline cannot express}
Entity generation and removal already exist, but they do not define task
arrival, ownership, completion, or reassignment.

\paragraph{Candidate capability}
A reusable task model with saved arrival schedules and common task events,
which would make these comparisons repeatable. It should first use the
existing interaction, autonomy, network, and metrics roles. Only a
demonstrated limitation would justify moving part of that model into the core.

\paragraph{Experiment}
Compare allocation methods under identical task arrivals, then increase
demand, team size, and interruptions. Completed tasks per unit time, waiting
time, backlog, and recovery after an agent is lost would reveal where
additional robots help or create congestion. This tests a research capability
beyond the baseline's runtime, even if no scheduler change is needed.
Continuing tasks do not by themselves require continual learning.

\section{Learned Policies and Accelerated Simulators}
\label{sec:learning}

Learned policies are now an expected baseline in multi-agent robotics, and the
simulators used to train them have changed more since SCRIMMAGE than any other
part of its design space. This section traces that change and then states our
position: SCRIMMAGE-RS is a CPU multi-agent testbed for studying decisions
under explicit sensing, estimation, communication, and vehicle constraints. It
could also supply experience to a separate learner when a learned decision is
itself the research question. No learning support is built yet. It, and any
GPU computation, should be built when an experiment needs it and measured on
that complete experiment.

\subsection{How the Field Has Moved}
\label{sec:learning-history}

\paragraph{Standard interfaces}
Gym and PettingZoo standardized how a learner steps an environment
\cite{terry2021pettingzoo}. They are interfaces, not architectures: both
support stepping many environments at once, and PettingZoo supports
simultaneous actions and agents that join or leave. SCRIMMAGE's OpenAI Gym
interface \cite{demarco2018} crossed between Python and C++ on every step,
rebuilt the simulation on every reset, and required a compiled C++ plugin for
each change to a reward or observation. It was removed from the maintained
branch in 2025, and we found no benchmark or result that depended on it. We
did not measure why it fell out of use. The simulation's own speed is an
unlikely cause: on one core, C++ SCRIMMAGE advances the straight-flight
mission of Section~\ref{sec:performance} at about 1.2 million agent-steps per
second, computed from the bare-metal timings of Appendix~\ref{app:performance}.
The overheads around each step and the cost of changing a task are plausible
causes, but remain hypotheses.

\paragraph{Many worlds on one GPU}
Isaac Gym, VMAS, and JaxMARL moved the simulation onto the GPU, advancing
thousands of independent worlds together
\cite{makoviychuk2021isaacgym,bettini2022vmas,rutherford2023jaxmarl}, with
reported speedups of several orders of magnitude over CPU implementations. The
constraint is regular data: computation expressed as compatible array
operations over bounded capacities. It does not require identical worlds. MJX,
for example, batches physical parameters across worlds, while structural
changes force recompilation \cite{mjxdocs}. VMAS and the MPE tasks in JaxMARL
include communication actions with optional noise. Madrona organizes batched
simulation as an entity-component-system engine whose simulators also run on
the CPU \cite{shacklett2023madrona}, and GPUDrive uses it for data-driven
driving with hundreds of agents per world \cite{kazemkhani2025gpudrive}.

Since 2025 the trend has been toward physical fidelity. Isaac Lab adds
photorealistic rendering and multi-frequency sensors \cite{mittal2025isaaclab},
and its 3.0 beta adds Newton as an experimental physics backend
\cite{isaaclab3backends}. Crazyflow simulates drone swarms in JAX
\cite{schuck2026crazyflow}. MuJoCo-Drones-Gym offers aerodynamic effects,
multiple drones, and camera observations on the CPU. Its GPU backend omits the
aerodynamic effects and leaves multiple drones and vision to future work
\cite{tayal2026mujocodrones}, which illustrates the cost of maintaining a
second backend. In these tools communication is an action channel or part of
the observation; queued network delivery with delay and loss is usually added
by co-simulation with a network simulator such as ns-3
\cite{burmeister2025defiance}.

\paragraph{Fast CPU environments, GPU learners}
A parallel line kept the simulation on the CPU and moved only learning to the
GPU. Sample Factory fed a GPU learner from asynchronous CPU workers
\cite{petrenko2020samplefactory}. PufferLib's environments, written in C, each
run above a million steps per second on one core, and its authors argue that
only physics-heavy environments are worth moving to a GPU
\cite{suarez2025pufferlib}. They also attribute the poor adoption of otherwise
useful environments to system dependencies and slow source builds. Whether a
simulator of many interacting agents reaches comparable training throughput
depends on observation construction, rewards, resets, and learning as well as
the step, and we have not measured it.

\paragraph{Separate evaluation stages}
The most recent change concerns evaluation rather than speed. SMACv2 showed
that success on a fixed benchmark may not require the observations it provides
\cite{ellis2023smacv2}, and robotics projects now separate fast training from
a more realistic stage that tests the policy. Pyquaticus trains maritime
capture-the-flag policies in a lightweight simulator that embeds MOOS-IvP
vehicle dynamics, then deploys them on uncrewed surface vehicles
\cite{crowley2025pyquaticus}. A connected-vehicle benchmark evaluates policies
in simulation, a digital twin, and hardware, and separates two causes of
degradation: differences between control stacks and increasing environmental
realism \cite{beerwerth2026zeroshot}. BVR Sim gives heterogeneous aircraft a
common tactical interface, desired heading, altitude, and speed, above
aircraft-specific controllers. A policy trained on one aircraft won 45.5\% of
engagements on four unseen aircraft with adapted controllers and 13.2\%
without \cite{sun2026bvrsim}. These are different aircraft within one flight
model, so the result supports the controller-level abstraction rather than
transfer across model fidelities.

These four developments are not competing architectures. The interface, where
computation runs, and whether evaluation is a separate stage are independent
choices, and one system can combine all three.

\subsection{What This Testbed Supports, and Why}
\label{sec:learning-support}

\paragraph{What is distinctive}
Communication and partial observability exist elsewhere. What SCRIMMAGE-RS
adds is an explicit pipeline from sensing, through message delivery and
estimation, to decisions: sensors produce readings, network plugins deliver
messages through per-subscriber queues, estimators form each agent's belief,
and autonomy reads only belief (Section~\ref{sec:estimation}). Beneath the
decision, vehicle-specific controllers and motion models apply their own
limits. Output is byte-identical at any worker count, and collision checks and
routing within an entity scale to thousands of agents in one world
(Section~\ref{sec:scaling}); sensing every other agent and dense radio traffic
remain expensive. Agreement with C++ verifies the port
(Section~\ref{sec:baseline}); it does not establish that the models are
physically realistic.

\paragraph{When learning here would be justified}
The test is whether an experiment in this testbed has a decision that a learned
policy could usefully make, and whether reproducing the relevant vehicle or
information behavior in another simulator would be substantial work. That is
most likely when the information and decision structure is the research
problem: learning when to transmit an
update and when old information suffices; allocating tasks or replanning under
incomplete, delayed observations; navigating or coordinating above
vehicle-specific controllers; and comparing learned and classical teammates
under the same mission, sensing, communication, and lifecycle rules. For such
studies, training directly here may be simpler than maintaining a matching task
in another simulator. Contact-rich manipulation, visual learning, and
low-level flight control are better served by specialist tools such as Isaac
Lab.

\paragraph{Where learning would connect}
The boundary we would keep is that SCRIMMAGE-RS supplies experience and a
separate learner updates the policy. The learner runs missions with its current
policy, collects what they record, updates the policy, and repeats. On-policy
methods such as PPO need, for each decision, the observation, the sampled
action and its probability, the reward, and whether the episode ended or was
cut short, all from the policy that collected them. Ordinary run output
records truth, events, and summaries, so this data would need an optional
record. \texttt{Simulation::step} returns the state before the step, so it
cannot serve as a learning step unchanged, and reset can start by rebuilding
the simulation, measured before anything more elaborate. The learner's
language and framework, where policies run during collection, and any batching
would be chosen once a concrete task makes their requirements clear.

\paragraph{Controller-level actions}
Autonomy plugins already write desired commands for a controller to follow,
and BVR Sim's result makes this a promising place for a learned policy. The
motion models do not yet share one tactical interface: SingleIntegrator takes
a world-frame velocity, the aircraft controllers take heading, speed, and
altitude, and Multirotor has only an open-loop motor-speed driver. A common
interface needs per-model adapters and a multirotor navigation controller.

\paragraph{GPU computation}
Three GPU extensions are separate. A planner plugin can already score
thousands of candidate trajectories in one GPU call, with no new interface.
Evaluating one policy for every agent in one call needs a per-phase batch
across entities, since each autonomy call otherwise presents one observation;
this is part of the shared computation proposed for RQ2. Batching independent
training worlds belongs to the learner and needs neither. The determinism
contract for any of them is repeated evaluation on a pinned backend and device,
invariant to worker count. Assembling each batch in entity order removes one
source of variation, batch composition, which dominates nondeterminism in LLM
inference \cite{he2025nondeterminism}; the kernels and any sampling must also
be deterministic. Agreement between CPU and GPU results and reproducible
training are separate tests.

\paragraph{Deciding whether to build it}
RQ1 (Section~\ref{sec:rq1}) is the natural candidate, and it needs no learning
code to begin. Agents reach targets that each senses only within a limited
range; they send target reports over a network with limited range and delay,
and an estimator adds received reports to belief. Run it first with classical
strategies, nearest known target and the existing auction assignment, and
sweep range, delay, and loss, measuring completion, collisions, and messages
sent. That result stands on its own. If it reveals a decision the classical
strategies handle poorly, such as when to transmit or which agent takes a
target under stale information, that decision becomes the learning
experiment: train a policy, freeze it, compare it with the classical
strategies on identical missions, and remove the messages to confirm it uses
them, as SMACv2 recommends. A familiar task such as cooperative navigation
could check the plumbing along the way, but would not by itself justify the
integration. If no such decision appears, learning remains a documented
extension point.

\paragraph{Imported policies}
A policy trained in another simulator could be run here for
learned-versus-classical comparisons. Its observation normalization, coordinate frames,
action meanings, decision period, and termination rules must match the
original task, and a fixed-size observation of every agent cannot accept a
larger team unless it was designed around a bounded set of neighbors.

\section{Discussion and Limitations}
\label{sec:discussion}

\subsection{What Would Justify an Upgrade?}

Each selected experiment should compare the retained baseline with the
proposed extension, state what the baseline can already express, and isolate
the feature's effect. SMACv2 shows why success on fixed scenarios is
insufficient: some original SMAC tasks admit useful time-only policies
\cite{ellis2023smacv2}. Use held-out layouts, task schedules, or team sizes,
and remove the relevant feedback or communication to check that it matters.
These controls can begin with the existing scenario and sweep tools.

The estimation stage (Section~\ref{sec:estimation}), on which RQ1 builds, is
the first core change; shared computation (RQ2) is the other candidate. Task models (RQ3) and evaluation cases should begin as research
plugins and experiment support. A focused paper could implement one of the core
candidates and answer its associated question, leaving the others as
motivated future work. Listing features or demonstrating that they run would
not establish their research value.

\subsection{Limits of the Baseline}

The C++ defects that Rust corrects are listed in Table~\ref{tab:differences},
and the regression Rust inherited in Section~\ref{sec:substeps}. The limits of
the parity claim are:
\begin{itemize}
\item \emph{Scope.} Parity covers the tested configurations of the retained
models, not the full C++ catalog.
\item \emph{Message contents.} Only lifecycle, collision, and sensor messages
are compared by content; other messages, such as auction bids, by delivery only.
\item \emph{Stochastic behavior.} Sensor noise is tested by seven marginal
distributions in one NoisyContacts fixture, not for temporal or cross-axis
dependence, and NoisyState noise is not tested by distribution.
\item \emph{Rounding.} Results agree to rounding, not bit for bit: C++ and Rust
call different math libraries and group some operations differently.
\end{itemize}

\section{Parity Details}
\label{app:parity}

\paragraph{Approach}
Both simulators run the same mission files. C++ comes from the current
\texttt{Ubuntu-24.04} branch, built headless in its own Docker image.

Trajectories alone can hide differences in what agents believe, what their
plugins command, and what messages they send. We therefore added an optional
trace to a separate C++ branch. It records each message delivery (tick,
sender, and receiver), the entities named in lifecycle and collision events,
published sensor readings, each agent's belief, and the commands each plugin
passes to the next. Other message contents, such as auction bids, are not
compared. Rust writes the same trace. Instrumentation that changed C++ would invalidate the
comparison, so every run is repeated on the unmodified build: frames and
summaries must be byte-identical.

Randomized runs only compare if both simulators draw the same random numbers.
The C++ standard leaves its default generator up to each compiler's library, so
the C++ branch can switch spawning to the same fully specified generator Rust
uses. Rust's sensor noise uses its own random streams by design, so noise is
compared by distribution instead of sample by sample.

A comparison that cannot fail proves nothing. Beyond fourteen hand-written
missions, we ran 100 randomly generated scenarios and ten long ones of up to
1{,}000~s, planted twelve plausible porting bugs to confirm the comparison
catches them, and tested the noise distributions. Appendix~\ref{app:method}
gives the details.

Table~\ref{tab:parity} summarizes the evidence. All curated missions and
generated scenarios pass, and every planted bug is detected. Two
message-delivery bugs (a message one tick late, local messages crossing
entities) changed trajectories in the previous campaign (2026-09-25) but no
longer do; only the summary and trace checks catch them now. We have not
isolated which later change caused this.
In passing runs,
trajectories agree to $1.8\times10^{-10}$~m at worst and usually to
$10^{-14}$~m or better. No difference was detected in seven NoisyContacts
marginal error distributions at the corrected significance threshold.

Eight of the ten long runs pass. The other two end about 0.2~mm and
$4\times10^{-8}$~m apart; perturbation experiments suggest numerical sensitivity

\section{Comparison Method}
\label{app:method}

\paragraph{Builds}
A checker builds each C++ branch from a \texttt{git archive} inside the
unmodified upstream dependency image (\texttt{linux/amd64}, GCC~13.3), headless
and single-threaded. \texttt{Ubuntu-24.04} is the unmodified reference;
\texttt{benchmarking-edits} adds opt-in comparison support and the substep
correction (Appendix~\ref{app:substeps}). A later
commit (\texttt{5777aeea1}) also makes AircraftPIDController use its given
timestep and lowers its default altitude derivative gain, matching Rust. The timestep change is a fix; the lower gain is
a tuning choice, checked on one aircraft after one upset
(\texttt{paper/data/aircraft-pid-upset}). A third commit
(\texttt{1c8595b91}) is the only change to model equations: FixedWing6DOF and
Multirotor computed forces and moments from the start-of-step state at every
RK4 stage, which made the step first order; both implementations now use each
stage's state (\texttt{paper/data/rk4-loads}). The campaign reported here
includes all three. Two command drivers exist in both implementations:
\texttt{MotorSpeeds}, because the upstream multirotor controller no longer
matches the multirotor model, and \texttt{ConstantVelocity}, because no retained
upstream autonomy commands a velocity. Rust runs at 1, 2, and 8 workers, with
recording, and with tracing; all must be byte-identical.

\paragraph{Trace}
Set with \texttt{SCRIMMAGE\_TRACE} in C++ and \texttt{-{}-trace} in Rust. It
records every message delivery (tick, network, topic, sender, receiver, and the
entities in lifecycle and collision events), every published sensor state and
covariance, each entity's belief when its frame is logged, and every output the
next plugin reads. Each mission runs on the unmodified build, the instrumented
build, and the instrumented build with tracing; all three must write
byte-identical frames and summaries.

\paragraph{Criteria}
Frames must contain the same entities at every tick. States, beliefs, and
sensor readings must agree within $10^{-8}$~m, $10^{-8}$~m/s, $10^{-9}$~rad, and
$10^{-9}$~rad/s; outputs within $10^{-8}$; covariances within $10^{-9}$;
summaries within $10^{-6}$. Deliveries must match exactly, in order. The
position limit was set at 27 times the largest difference then measured in a
passing run ($3.7\times10^{-10}$~m); the largest now is $2.4\times10^{-10}$~m.
They replace the original 0.01~m and $10^{-3}$, which let a planted
sub-micrometre bug through.

\paragraph{Random draws}
The C++ standard leaves the default random engine and the normal
distribution's algorithm to each standard library. The reference build's
library (GCC's) and the one Rust reproduces (LLVM's) differ in both. With
\texttt{SCRIMMAGE\_LIBCXX\_SPAWN\_RANDOM}, the C++ branch draws spawns from the
standard-defined \texttt{std::minstd\_rand} with the same normal algorithm as
Rust. Without it, the randomized mission differs by up to 8.42~m; with it, it
agrees to $1.4\times10^{-14}$~m. Sensor noise is compared with
fixed-bias, zero-noise fixtures and, separately, by distribution.

\paragraph{Long runs}
Ten generated scenarios run for 1{,}000~s (fixed-wing: 100~s at 0.01~s steps).
A run agrees if every check passes over its whole length. For a run that
diverges, a control changes Rust's initial roll, commanded speeds, and turning
radii by one unit in the last place, scales each controller loop's proportional
gain by $1+10^{-12}$, and measures when Rust diverges from itself. One-ulp
parameter changes alone perturb the state far less than the rounding difference
between C++ and Rust, and do not reach a controller loop directly.

In \texttt{generated-000}, one aircraft settles into a sustained pitch
oscillation at about 20~s. Its altitude loop never levels off, and its commanded
pitch rate alternates between about $+1$ and $-3.7$~rad/s every half second.
Any difference in that loop then grows about tenfold per second until it levels
off near 0.1~mm. C++ and Rust exceed the tolerance after 28.8~s and end
$2.0\times10^{-4}$~m apart, and the control does the same after 26.8~s,
ending $2.1\times10^{-4}$~m away (Table~\ref{tab:long}). This suggests
numerical sensitivity; it does not rule out a small difference between the
two implementations.

\texttt{generated-007} flies four FixedWing6DOF aircraft with
AircraftPIDController. It agreed throughout until both implementations lowered
that controller's altitude derivative gain, which changed the flight; computing
the aircraft's forces at every RK4 stage changed it again. C++ and
Rust now exceed the tolerance after 76.4~s and end $8.4\times10^{-9}$~m apart;
the control diverges much earlier, after 14.4~s, and ends $7.9\times10^{-7}$~m away
(Table~\ref{tab:long}). Again this suggests numerical sensitivity rather than a
porting error, with the same caveat. Before the substep
order was restored, \texttt{generated-009} also diverged, after 69~s; it now
agrees throughout.

\paragraph{Summaries and one exclusion}
A differing summary passes only if entity and collision counts match exactly,
and the Rust run's metrics messages reproduce the C++ summary under the C++
scoring rule and the Rust summary under Rust's documented rule
(\texttt{reference/metrics\_model.py}). For entities C++ destroys before
the first step, their first-step trace records are excluded and counted, because
C++ still runs them for that step. No other difference is excluded.

\section{The Substep Correction}
\label{app:substeps}

In \texttt{SimControl::run\_entities}, SCRIMMAGE interleaved controller and
motion substeps from its first public commit (August 2017) until commit
\texttt{c0a9f42b2} (``added gpu support'', December 2025):
\begin{verbatim}
autonomy                      once per tick
for each substep:
    controllers               read the state motion just wrote
    motion model
sensors, interactions, ...    once per tick
\end{verbatim}
That commit closed the controller loop before a new GPU motion call, which
advances all substeps at once, and passed each controller call the full tick
length; a later commit restored the substep length but kept the split. A
comment written afterward still describes the interleaved design. GPU motion
models need OpenCL and appear in two demonstration missions.

The derivative term vanishes when a controller call sees the same setpoint and
the same measurement as the previous one: in the split order, autonomy runs
once per tick and nothing moves between controller calls. A nested controller
can still shift an inner setpoint between calls (an outer loop's integral keeps
growing), so the inner derivative is small rather than exactly zero.

The comparison branch (\texttt{7129e47f5}) restores the interleaved loop and
disables GPU acceleration in CMake, which also disables its GPU network plugin;
the GPU sources remain but are not built. \texttt{reference\_check.py} requires
the unmodified and fixed C++ to write identical output only when a mission has
one substep. Before and after the Rust change, 31 of 35 missions and workloads
wrote byte-identical frames, events, summaries, and traces at 1, 2, and 8
workers; the four that changed are the substep workloads
(\texttt{paper/data/substep-order/}). Against the fixed C++, the two substep
missions agree to $4.8\times10^{-14}$ and $2.2\times10^{-14}$~m with matching
traces, and the unmodified C++ differs from the fixed build on both.

Timed against the previous revision, alternating run by run (a warm-up pair
and five timed pairs), no workload changed consistently on one worker. On eight
workers, the substep workloads were slower in every pair, by 1--4\% with 64
aircraft and 4--10\% with 512; the other workloads changed in both directions.

\section{Performance Details}
\label{app:performance}

Tables~\ref{tab:benchmark} and~\ref{tab:benchmark-native} time five workloads
(straight flight, ten controller and motion substeps, noisy state and contact
sensors, scheduled spawning with collisions, and collision checks among aircraft
spread over about a kilometre, so few collide and the population stays nearly
constant) on an Apple M2 Pro, first with
both simulators in one Linux container (\texttt{reference/benchmark.py}) and
then on bare-metal macOS, where C++ is built with Apple clang
against the library versions Ubuntu 24.04 ships
(\texttt{paper/data/benchmark-native/}). Rust output matches single-threaded
C++ in the first two workloads. The other three depend on random draws that the
C++ build makes differently without the comparison spawn stream, so their ratios
are not speed claims.
C++ is the comparison branch of Appendix~\ref{app:substeps}, so both simulators
run substeps in the same order.

Where outputs match, Rust with one thread is 1.2 to 1.7 times faster than C++
in the container and 1.05 to 1.4 times faster on bare metal, and it uses 2.0 to
6.0 times less memory. These timings include the estimation stage (its cost is
measured on its own in Section~\ref{sec:estimation}), which raised Rust's peak
memory, most with 128 sensing aircraft
(7.4 to 12.3~MiB in the container), where each keeps its own contact list. Two changes made while profiling contributed, both with
identical output: Rust no longer rebuilds each plugin's message-address name
every step, which had taken about a fifth of the time on straight flight, and
it runs single-worker phases without the thread pool (below). Before them,
native C++ was 1.25 times faster on straight flight.

C++ collision checking compares every pair of aircraft, twice, so its cost
grows with the square of the number of aircraft; Rust uses the spatial queries
of Section~\ref{sec:spatial}, by default the scan. From 1{,}024 to 2{,}048
aircraft, Rust's collision workload takes 2.7 to 2.8 times longer and C++'s
3.8 to 9.1 times longer. Eight workers barely help, because the check runs in
one sequential phase.

Parallel speedup depends on each phase carrying enough work. Every phase hands
entities to a thread pool and joins it, which profiling puts at about
35~\textmu s on bare metal and roughly ten times that in Docker's virtual
machine. On bare metal, eight Rust workers beat one with substeps at 1{,}024
aircraft, with sensors at 64 and 128 aircraft (3.2 times at 128), and with
collisions at 2{,}048 aircraft, but not on light workloads or with 32 sensing
aircraft; in the container, only with 128 sensing aircraft. The handoff cost about 7~\textmu s even with one worker,
so Rust now runs single-worker phases on the calling thread, a third faster on
light workloads.

C++'s own \texttt{multi\_threaded} mode is not reliable. It deadlocked in 14 of
224 runs, counting startup runs (each killed after 120~s and retried), its output with sensors differs
between identical runs, and it is slower than single-threaded C++ except with
64 or more sensing aircraft on bare metal and 128 in the container. Its entity worker waits on a condition variable without a predicate,
so a wake-up can be lost; we did not modify it, and single-threaded C++ is the
baseline.

\section{Rust Self-Consistency}
\label{app:self}

Rust results are byte-identical across 1, 2, and 8 workers, with and without
recording and tracing, and whether a scenario comes from XML, YAML, or Rust
code. Built for another operating system and processor (Linux/amd64 versus
macOS/arm64), events and summaries stay identical in all 248 runs checked and
trajectories differ by at most $5.6\times10^{-11}$~m, because each system's math
library rounds differently (\texttt{reference/platform\_check.py}). This is exact because workers own separate entities, every phase finishes
before the next starts, and random draws are tied to entities and plugins
rather than workers.

\section{The Workflow Example}
\label{app:rq2}

The C++ side used the unmodified \texttt{Ubuntu-24.04} reference image.
\texttt{create-scrimmage-project.py} generated the project, and
\texttt{generate-plugin.sh autonomy FollowNearest} generated the header,
source, parameter XML, and CMake file. The templates on this branch were
reformatted to \texttt{(>{}>{}> PLUGIN\_NAME < < <)}, which the generator's
substitution no longer matches, so four placeholders in the source and three in
the header had to be fixed by hand. The template's example logic already
follows the nearest opponent, so the plugin body is unchanged from it. Running
the plugin requires adding the build and header folders to
\texttt{SCRIMMAGE\_PLUGIN\_PATH} and \texttt{LD\_LIBRARY\_PATH}.
\texttt{run\_experiments.py} and \texttt{scrimmage\_runner.sh} both import
\texttt{scrimmage.utils}, which was removed from the branch, and need
\texttt{pyDOE}, \texttt{pandas}, and \texttt{tqdm}; the \texttt{scrimmage}
command has no option to set a mission variable. The sweep is therefore a
shell loop that writes one mission per speed with \texttt{sed}.
\texttt{paper/rq2/run-cpp.sh} repeats all of this in one command.

The Rust side is the book's first-plugin tutorial: \texttt{follow\_nearest.rs}
in the starter crate, three lines in its \texttt{lib.rs}, a 48-line YAML
mission, and a 9-line sweep file. The same sweep file runs locally with
\texttt{scrimmage sweep} or as Slurm array shards with
\texttt{scripts/bulk\_run.py}. Line counts exclude blank and comment lines;
the C++ count covers the header and source, not the generated CMake file.
Both place the two aircraft at fixed positions, and all four outcomes and
both catch times agree.

\section{Reproduction}
\label{app:reproduction}

From the repository root, with Docker and the sibling C++ checkout on both
branches, \texttt{python3 reference/campaign.py} reruns the C++ comparisons
(agreement matrix, sensitivity, noise, generated and long scenarios, platform),
replaces their folders in \texttt{paper/data/}, and regenerates the tables; with
\texttt{-{}-quick} it runs only the agreement matrix. The individual tools are
in \texttt{reference/}: \texttt{reference\_check.py} (matrix, traces, and
non-interference), \texttt{generate\_scenarios.py}, \texttt{sensitivity.py},
\texttt{noise\_statistics.py}, \texttt{divergence.py},
\texttt{platform\_check.py}, and \texttt{benchmark.py}. The compared missions
are listed in \texttt{reference/missions.txt}, and \texttt{reference/README.md}
documents the builds, tolerances, trace records, and how to add a model. The
C++ branch \texttt{benchmarking-edits} holds the instrumentation as
reviewable commits on top of \texttt{Ubuntu-24.04}.

The campaign does not rerun the rest: the timing in Tables~\ref{tab:benchmark}
and~\ref{tab:benchmark-native} (\texttt{reference/benchmark.py}, and
\texttt{build.sh} and \texttt{run.py} in \texttt{paper/data/benchmark-native/}), the workflow example
(\texttt{paper/rq2/run-cpp.sh} and \texttt{scrimmage sweep}), and the Rust and
Python test suites (\texttt{cargo test -{}-workspace} and
\texttt{python3 -m unittest discover -s reference -p 'test\_*.py'}).
